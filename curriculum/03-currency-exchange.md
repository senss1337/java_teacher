# Проект 3. Обмен валют

**ТЗ:** [zhukovsd — Обмен валют](https://zhukovsd.github.io/java-backend-learning-course/projects/currency-exchange/)

REST API (без веб-интерфейса) для валют и обменных курсов:
- `GET /currencies`, `GET /currency/EUR`, `POST /currencies` — список, одна валюта, добавление;
- `GET /exchangeRates`, `GET /exchangeRate/USDRUB`, `POST /exchangeRates`, `PATCH /exchangeRate/USDRUB` — курсы;
- `GET /exchange?from=USD&to=AUD&amount=10` — конвертация суммы. Курс ищется по трём сценариям:
  есть пара AB → берём её курс; есть BA → считаем обратный; есть USD-A и USD-B → считаем кросс-курс.
- Ошибки — JSON `{"message": "..."}` с правильным HTTP-кодом.

Технологии: **чистые Jakarta Servlets + JDBC + SQLite**, без фреймворков, деплой WAR в Tomcat на VPS.

**Зачем без фреймворков**, если ты знаешь FastAPI/Django? Чтобы понимать, что Spring делает за тебя. На собеседовании
спросят «как работает `DispatcherServlet`», и твой ответ будет «это сервлет, который я сам писал в проекте 3».

Перед проектом **обязательно** пройди [мостик М3](03-0-bridge-web-jdbc.md): сервлеты, фильтры, Jackson, JDBC, транзакции,
слои — всё объяснено там.

**Сколько времени:** 2–3 недели.

### 1. `BigDecimal` — деньги без потерь

**Простыми словами.** `double` хранит числа в двоичном виде, и 0.1 в нём неточно. Для денег это недопустимо.
`BigDecimal` хранит десятичное число точно: целое «неотмасштабированное значение» + **scale** (сколько знаков
после запятой). `12.50` — это 1250 и scale 2.

Главные правила:

```java
new BigDecimal("0.1");              // ✅ из строки — точно
BigDecimal.valueOf(0.1);            // ✅ через каноническое строковое представление double
new BigDecimal(0.1);                // ❌ 0.1000000000000000055511151231257827021181583404541015625

var a = new BigDecimal("1.0");
var b = new BigDecimal("1.00");
a.equals(b);                        // ❌ false — equals учитывает scale!
a.compareTo(b) == 0;                // ✅ true — сравнение значений

BigDecimal.ONE.divide(new BigDecimal("3"));                          // ❌ ArithmeticException: бесконечная дробь
BigDecimal.ONE.divide(new BigDecimal("3"), 6, RoundingMode.HALF_UP); // ✅ 0.333333 — указан scale и округление
BigDecimal.ONE.divide(new BigDecimal("3"), MathContext.DECIMAL64);   // ✅ 16 значащих цифр

new BigDecimal("14.505").setScale(2, RoundingMode.HALF_EVEN);        // 14.50 — «банковское» округление
new BigDecimal("14.505").setScale(2, RoundingMode.HALF_UP);          // 14.51 — «школьное»
```

**Когда округлять.** Промежуточные вычисления (обратный курс, кросс-курс) держи с запасом точности и округляй
**один раз в конце**, когда получаешь итоговую сумму для клиента. Если округлять на каждом шаге, ошибки накапливаются.

**В JSON.** Jackson сериализует `BigDecimal` как число; научная нотация (`1E+2`) лечится настройкой
`JsonGenerator.Feature.WRITE_BIGDECIMAL_AS_PLAIN`.

**В SQLite.** Настоящего типа `DECIMAL` в SQLite нет: там «type affinity», и `DECIMAL(6)` превратится в NUMERIC,
который может хранить значение как float. Изучи [Datatypes In SQLite](https://www.sqlite.org/datatype3.html),
раздел 3, и реши, как хранить курс без потерь (варианты: TEXT, INTEGER с фиксированным множителем).

> ⚠️ **Типичная ловушка:** `assertThat(result).isEqualTo(new BigDecimal("14.50"))` падает, когда результат `14.5`.
> В тестах — `isEqualByComparingTo(...)`.

### 2. Разбор запросов, которых нет «из коробки»

- **Путь с параметром.** `/currency/EUR` — в сервлетах нет роутинга с `{code}`. Мапишь сервлет на `/currency/*`
  и берёшь хвост через `req.getPathInfo()` (вернёт `/EUR`).
- **PATCH.** У `HttpServlet` нет `doPatch`. Переопредели `service(req, resp)`: если метод `PATCH` — вызови свой обработчик,
  иначе `super.service(...)`.
- **Тело PATCH в `x-www-form-urlencoded`.** Tomcat разбирает тело формы в `getParameter` только для POST.
  Для PATCH придётся прочитать тело (`req.getReader()`) и разобрать самому (`URLDecoder`).

### 3. Проектирование обработки ошибок

**Простыми словами.** По ТЗ у каждой ошибки есть код (400, 404, 409, 500) и тело `{"message": "..."}`.
Плохо: в каждом сервлете `try/catch` с выставлением кода. Хорошо: иерархия своих исключений, одно место трансляции.

```java
// Нейтральный пример: иерархия исключений приложения-библиотеки
abstract class LibraryException extends RuntimeException { ... }
class BookNotFoundException extends LibraryException { ... }         // → 404
class DuplicateIsbnException extends LibraryException { ... }        // → 409
class InvalidRequestException extends LibraryException { ... }       // → 400
```

Где их ловить и превращать в ответ? Варианты: фильтр, оборачивающий `chain.doFilter` в `try/catch`; абстрактный базовый
сервлет с шаблонным методом. Неожиданные исключения → 500 с общим текстом, а подробности только **в лог**
(stack trace клиенту не показываем: это утечка внутренностей).

**Логирование** — через SLF4J + Logback (как `logging` в Python), не `System.out`:

```java
private static final Logger log = LoggerFactory.getLogger(MyServlet.class);
log.error("Unexpected error on {}", req.getRequestURI(), e);   // {} — плейсхолдер, e — stack trace в лог
```

### 4. Тестирование сервиса без БД

Логика обмена (три сценария) живёт в сервисе. Сервис зависит от DAO **через интерфейс**, значит, в тесте DAO можно
подменить:
- **фейк** — своя простая реализация интерфейса на `HashMap`;
- **мок** — Mockito: `when(dao.findByPair("USD", "EUR")).thenReturn(Optional.of(rate))`.

Так тестируешь все сценарии за миллисекунды, без SQLite. Подробнее о моках — в проекте 5.

## Паттерны и принципы в фокусе

- **Слои MVC(S):** сервлет — HTTP; сервис — правила (в том числе три сценария поиска курса); DAO — только SQL.
- **DAO** за интерфейсом. Нужен ли интерфейс, если реализация одна? Сформулируй аргументы за и против (подсказка: тесты).
- **DTO + Mapper.** JSON-ответ ≠ строка таблицы. Где живёт маппинг?
- **Filter / Front Controller (Chain of Responsibility)** для общих вещей.
- **Иерархия исключений** + одна точка трансляции.
- **Composition root** в `ServletContextListener`; никаких `static getInstance()`.
- **Стратегии поиска курса** (три сценария) — кандидат на Chain of Responsibility / список стратегий, чтобы четвёртый
  сценарий добавлялся без переписывания трёх.

## За что будет 🔴

- `double`/`float` для денег и курсов; `new BigDecimal(double)`.
- Конкатенация SQL; незакрытые `Connection`/`Statement`/`ResultSet`.
- SQL в сервлетах; логика обмена в сервлете; изменяемые поля в сервлете.
- `SELECT` перед `INSERT` вместо ограничения в БД.
- Нет `UNIQUE`/`FOREIGN KEY`, выключенные внешние ключи в SQLite.
- Копипаста `setContentType`/`setCharacterEncoding` по сервлетам.
- Stack trace в ответе клиенту; `catch (Exception e) { e.printStackTrace(); }`.
- `static getInstance()`-синглтоны; новый `ObjectMapper` на каждый запрос.
- Коды или формат ответов не по ТЗ.
