# Проект 1. Виселица

**ТЗ:** [zhukovsd — Виселица](https://zhukovsd.github.io/java-backend-learning-course/projects/hangman/)

Консольная игра:
1. При старте меню: «новая игра» или «выход».
2. Новая игра: из словаря выбирается случайное слово.
3. Игрок вводит буквы. После каждой выводятся: счётчик ошибок, слово с открытыми буквами (`_ _ Р _ _`) и ASCII-рисунок виселицы.
4. Победа или поражение → снова меню.

Автор курса разрешает писать процедурно, через `static`-методы в `Main`. **Тебе — нельзя.** Игру ты напишешь в любом
случае. Цель проекта — научиться раскладывать даже маленькую программу на объекты с понятными ролями и покрывать
логику тестами. На этом фундаменте стоят все следующие проекты.

**Сколько времени:** 3–5 дней.

---

## Цели обучения

После проекта ты умеешь:
- отделять **правила игры** (модель) от **ввода-вывода** (консоль): модель можно протестировать без консоли,
  а консоль заменить на GUI, не трогая модель;
- передавать зависимости через конструктор (DI без фреймворков);
- читать файлы из ресурсов проекта так, чтобы это работало и из IDE, и из JAR;
- писать юнит-тесты на логику, включая «неудобные» вещи вроде случайности и ввода с клавиатуры.

## Что изучить до старта

### 1. Разделение модели и представления

**Простыми словами.** В любой программе с интерфейсом есть две разные вещи:
- **что происходит** — правила: угадал букву, ошибся, выиграл, проиграл;
- **как это показать** — напечатать в консоль, нарисовать в окне, отдать JSON.

Если смешать их в одном классе (в методе проверки буквы стоит `System.out.println("Ошибка!")`), получаем проблемы:
- модель не протестировать без перехвата консоли;
- чтобы сделать GUI, придётся переписывать правила;
- класс меняется по двум несвязанным причинам.

Последнее и есть **принцип единственной ответственности (SRP)**: у класса должна быть одна причина для изменения.

**Как это выглядит (нейтральный пример — термометр):**

```java
// ПЛОХО: модель сама печатает
class Thermostat {
    void setTemperature(int t) {
        this.t = t;
        if (t > 30) System.out.println("🔥 Жарко!");          // модель знает про консоль
    }
}

// ЛУЧШЕ: модель сообщает факт, а решать, как его показать, будет view
class Thermostat {
    void setTemperature(int t) { this.t = t; }
    boolean isOverheated() { return t > MAX_COMFORT; }      // вопрос к модели
}
class ConsoleView {
    void render(Thermostat th) {
        if (th.isOverheated()) System.out.println("🔥 Жарко!");
    }
}
```

**Tell, don't ask.** Не вытаскивай из объекта пять полей, чтобы снаружи вычислить «победа ли это». Спроси сам объект:
`game.isWon()`. Тогда правило «что такое победа» живёт в одном месте.

### 2. Внедрение зависимостей (DI) через конструктор

**Простыми словами.** Игре нужно слово. Откуда его взять — из файла, из сети, из списка в тестах — это **деталь**.
Если игра сама создаёт «читалку файла» внутри себя, она навсегда привязана к файлу, и в тесте ты не сможешь
подсунуть известное слово.

Решение: игра **получает** источник слов через конструктор и знает о нём только через **интерфейс**.
Это и есть Dependency Injection. Spring потом просто автоматизирует то же самое.

```java
// Нейтральный пример: отчёт, которому нужен источник данных
interface SalesSource { List<Sale> load(); }                   // контракт

class CsvSalesSource implements SalesSource { ... }             // реальная реализация
class FixedSalesSource implements SalesSource { ... }           // для тестов: отдаёт заранее заданный список

class Report {
    private final SalesSource source;                           // зависимость от АБСТРАКЦИИ
    Report(SalesSource source) { this.source = source; }        // получаем снаружи
    BigDecimal total() { ... source.load() ... }
}

// main — «точка сборки» (composition root): только здесь выбираются конкретные классы
var report = new Report(new CsvSalesSource(Path.of("sales.csv")));
// в тесте
var report = new Report(new FixedSalesSource(List.of(sale1, sale2)));
```

Это заодно паттерн **Strategy**: алгоритм «откуда взять данные» вынесен в отдельный объект и подменяется.

**Случайность — тоже зависимость.** `new Random()` внутри класса делает поведение непредсказуемым в тестах.
Передай `Random` (или `RandomGenerator`) в конструктор, и в тесте сможешь передать `new Random(42)`
с фиксированным **seed**: последовательность «случайных» чисел будет каждый раз одинаковой.

> 🎯 **Спросят на собесе:** Что такое Dependency Injection и почему конструкторная инъекция предпочтительнее сеттерной?
> **Ответ:** Объект получает зависимости снаружи, а не создаёт сам. Это позволяет подменять реализации (тесты)
> и соблюдать принцип инверсии зависимостей. Через конструктор зависимости обязательны, могут быть `final`, объект сразу валиден.
> **Типичная ошибка:** считать, что DI = Spring. DI — это принцип, Spring — лишь контейнер для него.

### 3. Состояние игры: `enum` и паттерн State

**Простыми словами.** У партии есть состояния: «идёт», «победа», «поражение». Хранить их строками (`"WIN"`)
или числами (`1`) плохо: опечатка не поймается компилятором. Для фиксированного набора значений в Java есть `enum`.

Иногда состояние определяет не только «что показать», но и **что можно делать**: в завершённой игре нельзя
делать ход. Если таких правил много, каждое состояние делают отдельным классом с одинаковым интерфейсом.
Это паттерн **State**. Для Виселицы достаточно `enum`, но ты должен уметь обосновать выбор.

```java
enum OrderStatus { NEW, PAID, SHIPPED, CANCELLED;
    boolean canBeCancelled() { return this == NEW || this == PAID; }   // у enum могут быть методы
}
```

**Вычислять или хранить?** Статус «победа» можно не хранить в поле, а **вычислять** из данных: все буквы слова
открыты → победа. Меньше полей — меньше шансов, что они разойдутся (например, `isWon = true`, а буквы открыты не все).

### 4. Чтение ресурсов

**Простыми словами.** Словарь лежит в `src/main/resources/words.txt`. При сборке Maven кладёт его **внутрь JAR**.
А внутри JAR это не файл на диске, поэтому `new File("src/main/resources/words.txt")` работает только из IDE,
а из JAR падает. Ресурсы читают через **classpath**:

```java
try (InputStream in = getClass().getResourceAsStream("/words.txt")) {          // "/" = от корня classpath
    if (in == null) throw new IllegalStateException("words.txt not found");     // ресурса нет → null, не исключение!
    var reader = new BufferedReader(new InputStreamReader(in, StandardCharsets.UTF_8));
    ...
}
```

Путь **со `/`** — от корня classpath; **без `/`** — относительно пакета класса. Это частая причина `null`.

### 5. Консольный ввод

`Scanner` удобен: `scanner.nextLine()`. Но его можно создать не только над `System.in`, а над любым `InputStream`.
Значит, в тесте можно подставить строку как «ввод пользователя»:

```java
var fakeInput = new ByteArrayInputStream("а\nб\nв\n".getBytes(StandardCharsets.UTF_8));
var scanner = new Scanner(fakeInput);            // в тесте вместо клавиатуры
```

Аналогично вывод: вместо `System.out` передай `PrintStream`, а в тесте — `PrintStream` над `ByteArrayOutputStream`
и проверь, что напечатано.

### Шпаргалка

| Тема | Зачем здесь | Обрати внимание |
|------|-------------|-----------------|
| `getResourceAsStream` | словарь в ресурсах | путь со `/` и без; `null`, если нет |
| `Scanner`, `BufferedReader` + `InputStreamReader` | ввод, чтение словаря | всегда `UTF_8` |
| `Random` / `RandomGenerator` | выбор слова | передавать снаружи ради тестов |
| `enum` с методами | статус игры | не строки и не `int` |
| `Set<Character>`, `Character.toLowerCase` | угаданные буквы | регистр, `ё`/`е` |
| Text blocks `"""` | ASCII-картинки | — |

## Паттерны и принципы в фокусе

- **SRP** — сколько причин для изменения у каждого твоего класса? «Поменяли словарь», «поменяли правила»,
  «сделали GUI вместо консоли» — каждое изменение должно затрагивать один класс.
- **Strategy / DIP** — игра зависит от контракта «дай слово», а не от файла.
- **State** — `enum`-статуса достаточно или нужны классы-состояния? Выбери и обоснуй.
- **Модель и представление** — модель не знает про консоль, отрисовщик не знает правил.
- **Tell, don't ask** — спрашивай игру, а не вычисляй за неё.

## Вехи

### Веха 1.1 — Модель игры и тесты

**Что нужно сделать**
1. Создать Maven-проект `projects/01-hangman/`.
2. Написать класс (или несколько), описывающий **одну партию**: загаданное слово, угаданные буквы, ошибки, лимит ошибок.
3. Операция «сделать ход буквой» и способы узнать состояние: слово с открытыми буквами, число ошибок, закончена ли игра, результат.
4. Покрыть модель тестами.

В этой вехе **нет** ни консоли, ни словаря: слово передаётся в конструктор прямо в тестах.

**С чего начать.** Не с класса, а с **теста**. Напиши первый тест словами, а потом кодом:
«создаю игру со словом "кот"; хожу буквой "о"; ожидаю, что маска слова — `_о_`, а ошибок 0».
Пусть не компилируется, потом создай класс и методы, чтобы тест прошёл. Затем следующий тест: «хожу буквой "ы" — ошибок 1».

**Вопросы для размышления**
1. Какие у игры **инварианты** (что всегда должно быть правдой)?
   *Направление: может ли число ошибок превысить лимит? Может ли игра продолжаться после победы?*
2. Повторный ввод уже названной буквы — это ошибка игрока или нет? Реши сам и зафиксируй в тесте и README.
3. Что должен вернуть «ход»: ничего (`void`), `boolean` «угадал ли», или `enum` с вариантами
   (угадал / не угадал / уже было)? Кому нужна эта информация?
   *Направление: консоли нужно как-то сказать игроку «эту букву вы уже вводили».*
4. Как отдать наружу множество угаданных букв так, чтобы его нельзя было изменить?
   *Направление: тема 2 модуля 0′, защитные копии и неизменяемые коллекции.*
5. Кто проверяет, что ввод — это одна русская буква (а не цифра или «аб»): модель или код ввода?
   *Направление: модель должна защищать свои инварианты от любого вызывающего, но сообщения «введите одну букву»
   к правилам игры не относятся.*

**Как проверить себя**
- [ ] В классах модели нет `System.out`, `Scanner` и вообще ничего из `java.io`.
- [ ] Все поля `private`, где возможно — `final`. Сеттеров нет.
- [ ] Тесты: угадал букву; не угадал; повтор; победа; поражение; ход после окончания игры; буква в другом регистре;
      невалидный символ. Однотипные кейсы — через `@ParameterizedTest`.
- [ ] Статус «победа/поражение» вычисляется, а не хранится отдельным полем (или у тебя есть обоснование).
- [ ] `./mvnw verify` зелёный.

**Что прислать:** «сдаю веху 1.1».

### Веха 1.2 — Словарь

**Что нужно сделать**
1. Найти словарь русских существительных в именительном падеже (поищи «список существительных txt»).
   Положить в `src/main/resources/`.
2. Отфильтровать слишком короткие слова по понятному правилу (например, короче 5 букв), убрать дефисы, пробелы и т. п.
3. Сделать источник слов, который отдаёт случайное слово.
4. Игра получает источник через интерфейс.

**С чего начать.** Опиши интерфейс источника слов: какие у него методы, что они возвращают.
Затем напиши тест с **тестовым** словарём из 3 слов в `src/test/resources/` и фиксированным `Random`.

**Вопросы для размышления**
1. Загружать словарь один раз или перед каждой игрой? Где он живёт, пока программа работает?
2. Что делать, если файла нет или после фильтрации он пуст? Где и с каким исключением упасть?
   *Направление: лучше упасть сразу при старте с понятным сообщением, чем посреди игры.*
3. Как проверить тестом, что выбор случайный, но при этом тест стабилен?
   *Направление: seed.*

**Как проверить себя**
- [ ] Словарь читается через classpath (`getResourceAsStream`), с `UTF_8`, поток закрывается (try-with-resources).
- [ ] `./mvnw package && java -jar target/*.jar` — словарь находится (проверишь окончательно в 1.4, когда будет `main`).
- [ ] Игра зависит от интерфейса источника слов, а не от конкретного класса.
- [ ] Тесты на фильтрацию и на отсутствующий/пустой словарь.

### Веха 1.3 — Консоль и отрисовка

**Что нужно сделать**
1. Класс, который рисует текущее состояние: маску слова, ошибки, использованные буквы, ASCII-виселицу.
2. Класс/метод, который читает ход игрока, валидирует ввод и повторяет запрос при мусоре.
3. 7 стадий виселицы (0–6 ошибок) в виде текста.

**С чего начать.** Нарисуй стадии в текстовом редакторе. Потом подумай, как по числу ошибок получить нужную стадию.

**Вопросы для размышления**
1. Как сопоставить число ошибок и картинку **без** цепочки из 7 `if`?
   *Направление: что естественнее всего индексируется числом от 0 до 6?*
2. Кто отвечает за «повторите ввод»: цикл ввода или модель?
3. Как протестировать ввод-вывод?
   *Направление: раздел 5 «Консольный ввод» выше. `Scanner` над `ByteArrayInputStream`, вывод в `ByteArrayOutputStream`.*

**Как проверить себя**
- [ ] Отрисовщик получает то, что нужно для отрисовки, и не содержит правил игры (не решает, победа ли).
- [ ] Невалидный ввод не роняет программу и не считается ошибкой игрока.
- [ ] Нет магических чисел: лимит ошибок, минимальная длина слова — именованные константы.
- [ ] Хотя бы один тест на ввод с «мусором».

### Веха 1.4 — Игровой цикл, меню, финал

**Что нужно сделать**
1. Меню: новая игра / выход, повтор после окончания партии.
2. `main` собирает объекты и запускает игру.
3. Исполняемый JAR, `README.md`.
4. Самопроверка по [чеклисту из ТЗ](https://zhukovsd.github.io/java-backend-learning-course/projects/hangman/#чеклист-для-самопроверки)
   (только после того, как всё работает!).

**С чего начать.** Напиши `main` так, как хотел бы его видеть: 3–5 строк, создающие объекты и запускающие цикл.
Затем реализуй недостающее.

**Как проверить себя**
- [ ] `main` — 3–5 строк, никакой логики.
- [ ] Никакого изменяемого `static`-состояния во всём проекте.
- [ ] `./mvnw verify` зелёный; `java -jar target/*.jar` запускает игру, кириллица отображается нормально.
- [ ] README: как запустить, правила (как обрабатываются повторы и регистр).
