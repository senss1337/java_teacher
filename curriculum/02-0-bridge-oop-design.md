## Часть 1. SOLID на пальцах

SOLID — пять принципов, которые помогают писать код, который легко менять. Не заучивай формулировки:
пойми, **какую боль** снимает каждый принцип.

### S — Single Responsibility (единственная ответственность)

**Боль:** один класс меняется по разным причинам, правка одного ломает другое.

```java
// ПЛОХО: отчёт считает, форматирует и сохраняет
class SalesReport {
    BigDecimal total(List<Sale> sales) { ... }        // бизнес-правило
    String toHtml(List<Sale> sales) { ... }           // представление
    void saveToFile(String html, Path p) { ... }      // инфраструктура
}
```

Поменяли вёрстку — трогаем класс с бизнес-логикой. Поменяли способ сохранения — снова он.
**Лучше:** `SalesCalculator`, `HtmlReportFormatter`, `ReportStorage`. Каждый меняется по своей причине.

Вопрос-проверка: «опиши класс одним предложением без союза "и"».

### O — Open/Closed (открыт для расширения, закрыт для изменения)

**Боль:** добавление нового варианта требует правки старого, проверенного кода, и в нём появляются баги.

```java
// ПЛОХО: каждый новый способ доставки — правка этого метода
BigDecimal cost(Order o) {
    if (o.delivery().equals("COURIER")) return ...;
    else if (o.delivery().equals("POST")) return ...;
    else if (o.delivery().equals("PICKUP")) return ...;   // и так далее
}

// ЛУЧШЕ: новый способ = новый класс, старый код не трогаем
interface DeliveryMethod { BigDecimal cost(Order o); }
class Courier implements DeliveryMethod { ... }
class Post implements DeliveryMethod { ... }
```

### L — Liskov Substitution (подстановка Лисков)

**Боль:** наследник формально подходит по типу, но ведёт себя неожиданно, и код, написанный для родителя, ломается.

```java
class Bird { void fly() { ... } }
class Penguin extends Bird {
    @Override void fly() { throw new UnsupportedOperationException(); }   // сюрприз!
}
void migrate(List<Bird> birds) { birds.forEach(Bird::fly); }   // упадёт на пингвине
```

Если наследнику приходится «отключать» метод родителя, иерархия построена неверно. Здесь нужно разделение:
`Bird` и отдельный интерфейс `Flying`. Правило: наследник **не усиливает требования** к входу, **не ослабляет
обещания** на выходе и сохраняет инварианты родителя.

### I — Interface Segregation (разделение интерфейсов)

**Боль:** класс вынужден реализовывать методы, которые ему не нужны.

```java
interface Worker { void work(); void eat(); void sleep(); }
class Robot implements Worker { void eat() { /* ??? */ } }         // заглушки = запах
```

Лучше несколько маленьких интерфейсов (`Workable`, `Feedable`): класс реализует только то, что умеет.

### D — Dependency Inversion (инверсия зависимостей)

**Боль:** высокоуровневая логика жёстко привязана к деталям (конкретной БД, файлу, консоли), не протестировать и не заменить.

Ты уже делал это в Виселице: игра зависит от интерфейса источника слов, а не от файла.
Правило: **зависимости направлены к абстракциям**. Конкретные классы выбираются в одном месте — в **composition root**
(обычно `main`), там все объекты создаются и связываются.

> 🎯 **Спросят на собесе:** Что такое принцип подстановки Лисков? Пример нарушения?
> **Ответ:** Объекты подтипа должны заменять объекты базового типа без изменения корректности программы: наследник
> не усиливает предусловия, не ослабляет постусловия, сохраняет инварианты. Классика нарушения — `Square extends Rectangle`
> с сеттерами; ещё пример — наследник, вынужденно бросающий `UnsupportedOperationException`.

## Часть 2. Наследование vs композиция

**Простыми словами.**
- **Наследование** — «является»: `Dog extends Animal`. Наследник получает всё, что есть у родителя, и зависит от его внутренностей.
- **Композиция** — «имеет»: `Car` **содержит** `Engine` в поле. Машина пользуется двигателем через его публичные методы.

**Почему «предпочитай композицию».** Наследник видит `protected`-детали родителя. Изменишь родителя — могут сломаться
все наследники (это называют «хрупкий базовый класс»). Наследование фиксируется при компиляции: поведение `Dog`
в рантайме не поменять. Композиция позволяет собрать объект из «деталей» и менять их.

**Когда наследование уместно:** настоящее «is-a», наследник полностью соблюдает контракт родителя (LSP), родитель
спроектирован для наследования (абстрактный класс с понятными точками расширения).

**Пример: общий код без копипасты.** Два класса делают похожее, но немного по-разному.

```java
// Вариант А — наследование с шаблоном (Template Method, см. часть 3)
abstract class DataExporter {
    public final void export(List<Row> rows) {          // final: скелет не переопределить
        var filtered = rows.stream().filter(this::include).toList();
        write(format(filtered));
    }
    protected abstract boolean include(Row r);          // шаги — у наследников
    protected abstract String format(List<Row> rows);
    private void write(String s) { ... }                // общий шаг
}

// Вариант Б — композиция со стратегиями
class DataExporter {
    private final Predicate<Row> filter;
    private final Function<List<Row>, String> formatter;
    DataExporter(Predicate<Row> filter, Function<List<Row>, String> formatter) { ... }
}
```

Оба варианта законны. А: хорош, когда варианты — устойчивые «виды» с общим смыслом. Б: когда части комбинируются
свободно (любой фильтр × любой формат).

> 🎯 **Спросят на собесе:** Композиция vs наследование: почему «предпочитай композицию»?
> **Ответ:** Наследование создаёт сильную связь с реализацией родителя (хрупкий базовый класс), фиксируется при
> компиляции и нарушает инкапсуляцию. Композиция позволяет собирать поведение из частей и менять его в рантайме.
> Наследование оправдано для настоящего отношения «is-a» с соблюдением LSP.
> **Типичная ошибка:** «наследование — это плохо». Нет, плохо — наследование ради переиспользования кода.

## Часть 3. Шесть паттернов

**Что такое паттерн.** Типовое решение типовой проблемы, у которого есть имя. Ценность имени: говоришь коллеге
«здесь Strategy», и он сразу понимает структуру. Для каждого паттерна ниже: **проблема → идея → пример → когда не надо**.

### Strategy (Стратегия)

- **Проблема:** есть несколько взаимозаменяемых способов что-то сделать (рассчитать скидку, отсортировать,
  найти маршрут), и выбор между ними — цепочкой `if`.
- **Идея:** каждый способ — отдельный класс с общим интерфейсом; объект-пользователь получает нужный снаружи.

```java
interface DiscountPolicy { BigDecimal apply(BigDecimal price); }
class NoDiscount implements DiscountPolicy { ... }
class BlackFriday implements DiscountPolicy { ... }

class Checkout {
    private final DiscountPolicy discount;
    Checkout(DiscountPolicy discount) { this.discount = discount; }
    BigDecimal total(Cart c) { return discount.apply(c.sum()); }
}
```

- **Когда не надо:** вариант один и других не предвидится. В Java 8+ простую стратегию часто заменяет лямбда
  (`Function`, `Predicate`).

### State (Состояние)

- **Проблема:** поведение объекта зависит от его состояния, и в каждом методе `switch (state)`.
- **Идея:** каждое состояние — класс с одинаковым интерфейсом; объект делегирует вызовы текущему состоянию,
  а состояние может сменить себя на другое.

```java
interface PlayerState { PlayerState pressPlay(); String label(); }
class Stopped implements PlayerState {
    public PlayerState pressPlay() { return new Playing(); }
    public String label() { return "⏹"; }
}
class Playing implements PlayerState {
    public PlayerState pressPlay() { return new Paused(); }
    public String label() { return "▶"; }
}
```

- **Когда не надо:** состояний 2–3 и поведение почти не отличается — хватит `enum`.

### Template Method (Шаблонный метод)

- **Проблема:** несколько классов выполняют одинаковый алгоритм, отличаются отдельные шаги, и код скелета копируется.
- **Идея:** скелет — `final`-метод в абстрактном родителе, изменяемые шаги — абстрактные (или с реализацией по умолчанию)
  `protected`-методы. Пример — `DataExporter` в части 2.
- **Когда не надо:** шаги комбинируются свободно — тогда композиция и стратегии.

### Command (Команда)

- **Проблема:** нужно работать с действиями как с данными: хранить список действий, выполнять по очереди,
  откладывать, отменять.
- **Идея:** каждое действие — объект с методом `execute()`.

```java
interface Command { void execute(Document doc); }
class InsertText implements Command { ... }
class DeleteLine implements Command { ... }

List<Command> macro = List.of(new InsertText("Hello"), new DeleteLine(3));
macro.forEach(cmd -> cmd.execute(doc));     // исполнитель не знает конкретных команд
```

- **Когда не надо:** одно действие, которое не нужно хранить и комбинировать.

### Factory (Фабрика)

- **Проблема:** создание объекта сложное (параметры из конфига, случайные значения, выбор подкласса),
  и эта логика размазана по коду.
- **Идея:** вынести создание в отдельный метод или класс.

```java
class EnemyFactory {
    private final RandomGenerator random;
    EnemyFactory(RandomGenerator random) { this.random = random; }
    Enemy createGoblin() { return new Goblin(random.nextInt(10, 20)); }   // HP из диапазона
}
```

- **Когда не надо:** `new X(a, b)` и так понятен.

### Observer (Наблюдатель)

- **Проблема:** когда в объекте что-то происходит, должны отреагировать другие (логгер, UI, статистика),
  но объект не должен о них знать.
- **Идея:** объект хранит список подписчиков с общим интерфейсом и оповещает их.

```java
interface OrderListener { void onPaid(Order o); }
class OrderService {
    private final List<OrderListener> listeners = new ArrayList<>();
    void subscribe(OrderListener l) { listeners.add(l); }
    void pay(Order o) { ...; listeners.forEach(l -> l.onPaid(o)); }
}
```

- **Когда не надо:** подписчик всегда один и известен — просто вызови его.

### Анти-паттерн: Singleton через `static`

«Единственный экземпляр» через `private static final INSTANCE` + `getInstance()` выглядит удобно, но это глобальная
переменная: зависимость не видна из конструктора, в тестах её не подменить. «Один экземпляр на приложение» лучше
обеспечивать, создав объект один раз в composition root и передав всем, кому нужно.

## Часть 4. UML-диаграмма классов — чтобы рисовать дизайн до кода

Рисовать дизайн полезно **до** кода: на схеме ошибки видны раньше. Минимум нотации:

```
┌───────────────┐          «interface»
│   Checkout    │◆───────> DiscountPolicy       ◆──>  композиция (содержит)
├───────────────┤              △                ──▷   реализация / наследование (треугольник)
│ - discount    │              │ (пунктир)      ──>   зависимость (использует)
├───────────────┤       ┌──────┴──────┐
│ + total(cart) │   NoDiscount   BlackFriday
└───────────────┘
```

Инструменты: [Mermaid classDiagram](https://mermaid.js.org/syntax/classDiagram.html) (рендерится прямо в GitHub),
PlantUML или просто бумага. В README Симуляции будет нужна такая схема.

## Часть 5. Потоки: минимум для Симуляции

### Простыми словами

**Поток (thread)** — отдельная линия выполнения внутри программы. В Python из-за GIL потоки не исполняют байткод
по-настоящему параллельно. **В Java нет GIL**: потоки реально работают одновременно на разных ядрах.
Это даёт скорость, но и новые классы ошибок.

**Гонка (race condition).** Два потока одновременно выполняют `count++`. Это три шага: прочитать, прибавить, записать.
Оба прочитали 5, оба записали 6. Одно увеличение потерялось.

**Видимость.** Каждое ядро может держать копию переменной в своём кеше. Поток А поставил `running = false`,
а поток Б продолжает видеть `true` и крутится вечно. Без синхронизации Java **не гарантирует**, что один поток
увидит изменения другого.

**Инструменты:**
- **`volatile`** у поля — гарантирует **видимость**: запись одного потока сразу видна другим. Но не делает `count++`
  атомарным. Годится для флагов вида «остановись».
- **`synchronized`** — блок/метод, который выполняет только один поток за раз (захватывается «монитор» объекта).
  Даёт и атомарность, и видимость.
- **`AtomicInteger`, `AtomicBoolean`** — атомарные операции без явной блокировки (`incrementAndGet()`).
- **`wait()/notify()`** (низкоуровнево) или `ReentrantLock` + `Condition` / `CountDownLatch` / `Semaphore`
  (высокоуровнево) — чтобы поток **ждал** события, не нагружая процессор.

**Happens-before** — формальное правило Java Memory Model: если действие А happens-before действия Б, то Б гарантированно
видит результат А. Такое отношение создают: запись и последующее чтение `volatile`-поля; выход из `synchronized`
и последующий вход в него же на том же объекте; `thread.start()` и первые действия запущенного потока.

### Пример: остановка фонового потока

```java
class Ticker implements Runnable {
    private volatile boolean running = true;          // без volatile поток может никогда не увидеть false

    public void run() {
        while (running) {
            System.out.println("tick");
            try { Thread.sleep(1000); }
            catch (InterruptedException e) {           // нас попросили прерваться
                Thread.currentThread().interrupt();    // восстановить флаг прерывания и выйти
                return;
            }
        }
    }
    public void stop() { running = false; }
}

var ticker = new Ticker();
var thread = new Thread(ticker);
thread.start();          // run() начинает выполняться в НОВОМ потоке
// ... основной поток занят своим, например читает ввод
ticker.stop();
```

**Пауза без busy-wait.** `while (paused) {}` жжёт 100% ядра. Поток должен **заснуть** до сигнала: `wait()/notifyAll()`
на общем мониторе или `Condition.await()/signalAll()`. Ждать всегда **в цикле `while`**, а не в `if`: поток может
проснуться «просто так» (spurious wakeup), да и условие к моменту пробуждения могло снова поменяться.

### Частые ошибки
- Обычный `boolean` как флаг остановки между потоками.
- Busy-wait.
- `Thread.sleep` как способ «синхронизироваться».
- Проглатывать `InterruptedException`.
- `Thread.stop()` (устарел и опасен).

> 🎯 **Спросят на собесе:** Что делает `volatile`? Достаточно ли его для счётчика `count++`?
> **Ответ:** Гарантирует видимость записи другим потокам и запрещает переупорядочивание вокруг обращения (happens-before).
> Атомарности составных операций не даёт: `count++` — это чтение-изменение-запись; нужен `AtomicInteger` или блокировка.
> **Типичная ошибка:** «`volatile` делает переменную потокобезопасной».

> 🎯 **Спросят на собесе:** Почему `wait()` вызывают в цикле `while`, а не в `if`?
> **Ответ:** Из-за spurious wakeups и того, что условие могло измениться между `notify` и захватом монитора.
> Условие надо перепроверить после пробуждения.

2. **Strategy + Factory.** Генератор паролей с разными политиками (только цифры, буквы+цифры, с символами),

   (у команды есть `undo()`, история в `ArrayDeque`).
5. **Observer.** Банковский счёт оповещает подписчиков о снятии > 10 000 (SMS-заглушка, журнал аудита).
   Подписчики добавляются без изменения класса счёта.
6. Mermaid-диаграмма классов упражнения 4 в README.
