## Тема 1. Статическая типизация, примитивы и обёртки

### Простыми словами

В Python переменная — это просто имя, которое можно привязать к чему угодно: `x = 5`, потом `x = "hello"`.
В Java у переменной есть **тип**, он объявляется один раз и больше не меняется. Компилятор проверяет, что ты
никогда не кладёшь в переменную что-то не того типа. Это и есть **статическая типизация**.

Второе отличие: в Python всё объект, даже `5`. В Java есть два мира:
- **Примитивы** — `int`, `long`, `double`, `boolean`, `char`, `byte`, `short`, `float`. Это «голые» значения:
  быстрые, без методов, **не могут быть `null`**.
- **Объекты** — всё остальное, включая **классы-обёртки** над примитивами: `Integer`, `Long`, `Double`, `Boolean`...
  Обёртки нужны там, где требуется объект, например в коллекциях: `List<int>` написать нельзя, только `List<Integer>`.

Java сама превращает `int` ↔ `Integer`, когда нужно. Это называется **autoboxing / unboxing**. Удобно, но с подвохами (ниже).

Третье: числа в Java **ограничены**. `int` — 32 бита (примерно ±2,1 млрд), `long` — 64 бита. Python-овский `int`
безразмерный, а в Java при переполнении число **молча** «перекручивается» в отрицательное.

### Как в Python → как в Java

```python
# Python
x = 10
x = "text"             # можно
big = 2**31            # 2147483648 — без проблем
n = None
```

```java
// Java
int x = 10;
x = "text";                      // ОШИБКА КОМПИЛЯЦИИ: incompatible types
int big = Integer.MAX_VALUE + 1; // -2147483648 — переполнение, без ошибки!
int n = null;                    // ОШИБКА КОМПИЛЯЦИИ: примитив не может быть null
Integer boxed = null;            // можно, это объект
var y = 10;                      // var: тип (int) выводит компилятор, он всё равно статический
```

### Пример: три подвоха обёрток

```java
Integer a = 127, b = 127;
System.out.println(a == b);        // true  — Java кеширует объекты Integer от -128 до 127
Integer c = 128, d = 128;
System.out.println(c == d);        // false — два РАЗНЫХ объекта, == сравнивает ссылки
System.out.println(c.equals(d));   // true  — сравнение значений. Объекты сравнивай ТОЛЬКО через equals

Integer maybe = null;
int value = maybe;                 // NullPointerException: unboxing null

System.out.println(7 / 2);         // 3   — деление int на int целочисленное
System.out.println(7 / 2.0);       // 3.5
System.out.println(0.1 + 0.2);     // 0.30000000000000004 — double неточен, для денег не годится
```

Защита от переполнения: `Math.addExact(a, b)` бросит `ArithmeticException` вместо молчаливой ошибки.

### Частые ошибки
- `==` для `Integer`, `Long`, `String` — работает на маленьких числах и «внезапно» ломается на больших.
- `double` для денег. Нужен `BigDecimal` (подробно в проекте 3) или целые копейки в `long`.
- Не ждать переполнения в суммах и счётчиках.
- `char` — это не «символ» в человеческом смысле, а 16-битная единица UTF-16. Эмодзи занимает **два** `char`.

> 🎯 **Спросят на собесе:** Что выведет `Integer a = 127, b = 127; a == b` и то же для 128?
> **Ответ:** `true` и `false`. `==` сравнивает ссылки; `Integer.valueOf` кеширует -128..127. Объекты сравнивают через `equals`.
> **Типичная ошибка:** «оба true, это же числа».

> 🎯 **Спросят на собесе:** Почему `0.1 + 0.2 != 0.3` и что использовать для денег?
> **Ответ:** `double` — двоичная плавающая точка IEEE 754, 0.1 в ней точно непредставимо. Для денег — `BigDecimal`
> (создавать из строки или через `BigDecimal.valueOf(double)`, не `new BigDecimal(double)`) либо целые минимальные единицы (`long` копеек).

- EJ 61 (примитивы предпочтительнее упакованных типов), EJ 60 (избегайте `float`/`double` для точных ответов).

## Тема 2. Классы, объекты, инкапсуляция

### Простыми словами

Класс в Java очень похож на класс в Python: поля + методы + конструктор. Главная разница — в **контроле доступа**.

В Python `_balance` — это вежливая просьба «не трогай». Любой может написать `account._balance = -100`.
В Java `private` — это **запрет компилятора**: код снаружи класса физически не может обратиться к полю.

Четыре уровня доступа, от закрытого к открытому:
- `private` — только внутри этого класса;
- *без модификатора* (package-private) — внутри того же пакета;
- `protected` — пакет + классы-наследники;
- `public` — все.

**Правило Java:** всё закрыто по умолчанию, открываешь только то, что действительно нужно снаружи.

Зачем? Чтобы класс сам защищал свои **инварианты** — условия, которые всегда должны быть истинны. Например,
«баланс счёта не отрицательный». Если поле `balance` публичное, любой код его сломает. Если приватное и меняется только
через `withdraw()`, проверка в одном месте и обойти её нельзя.

**Геттеры и сеттеры — не инкапсуляция.** Частая ошибка новичков: сделать все поля `private` и на каждое сгенерировать
`getX()` и `setX()`. Это то же публичное поле, только длиннее. Сеттер оставляй, только если у изменения нет бизнес-правил.
Вместо `setBalance(x)` нужны осмысленные операции: `deposit(amount)`, `withdraw(amount)`.

**`static`** — член класса, а не объекта. `static`-поле одно на всю программу (как переменная модуля в Python),
`static`-метод вызывается без объекта (`Math.max(1, 2)`). Не делай всё `static`: это возврат к процедурному стилю.

**`final`** у поля: присвоить можно только один раз, в конструкторе. Если все поля `final` и нет методов, которые
меняют состояние, объект **иммутабельный** (неизменяемый).

### Как в Python → как в Java

```python
class Account:
    def __init__(self, owner, balance=0):
        self.owner = owner
        self._balance = balance          # «приватное» по договорённости

    def withdraw(self, amount):
        if amount > self._balance:
            raise ValueError("Недостаточно средств")
        self._balance -= amount
```

```java
public class Account {
    private final String owner;          // final: владелец не меняется после создания
    private long balance;                // private: снаружи недоступно в принципе

    public Account(String owner, long initialBalance) {   // конструктор = __init__
        if (initialBalance < 0) throw new IllegalArgumentException("balance < 0");
        this.owner = owner;
        this.balance = initialBalance;
    }

    public void withdraw(long amount) {  // осмысленная операция вместо setBalance
        if (amount > balance) throw new IllegalStateException("Недостаточно средств");
        balance -= amount;
    }

    public long balance() { return balance; }   // только чтение
}
```

### Пример: иммутабельный класс и защитная копия

```java
public final class Team {                          // final class: нельзя унаследоваться и «испортить»
    private final String name;
    private final List<String> members;

    public Team(String name, List<String> members) {
        this.name = name;
        this.members = List.copyOf(members);        // ЗАЩИТНАЯ КОПИЯ: снаружи список уже не изменить
    }

    public List<String> members() { return members; }   // List.copyOf неизменяемый, отдавать безопасно

    public Team withMember(String newMember) {       // «изменение» = новый объект
        var copy = new ArrayList<>(members);
        copy.add(newMember);
        return new Team(name, copy);
    }
}
```

Без `List.copyOf` вызывающий мог бы сохранить свой список и потом менять его, а вместе с ним и «неизменяемую» команду.

**Статическая фабрика и Builder** — два способа создавать объекты удобнее, чем конструктором:
- `Money.of(100, "RUB")` — у метода есть имя, он может кешировать объекты или вернуть подкласс (EJ 1);
- Builder — когда полей много и часть необязательна:
  `Pizza.builder().size(30).cheese(true).build()` читается лучше, чем `new Pizza(30, true, false, null, 2)` (EJ 2).

### Частые ошибки
- Публичные поля или геттер+сеттер на каждое поле.
- Геттер, возвращающий внутренний изменяемый список: вызывающий меняет состояние объекта в обход правил.
- Всё `static`.
- Нет валидации в конструкторе: объект можно создать в некорректном состоянии.

> 🎯 **Спросят на собесе:** Как сделать класс иммутабельным?
> **Ответ:** `final` класс (или приватный конструктор), все поля `private final`, нет сеттеров, изменяемые поля —
> защитные копии на входе и выходе (или неизменяемые коллекции), `this` не утекает из конструктора.
> **Типичная ошибка:** забыть про защитное копирование `List`/`Date` в геттере.

> 🎯 **Спросят на собесе:** Чем package-private отличается от `protected`?
> **Ответ:** package-private (без модификатора) — доступ только внутри пакета. `protected` — пакет + наследники в любых пакетах.

## Тема 3. `equals`, `hashCode`, `toString`, `Comparable`

### Простыми словами

В Java два вида «равенства»:
- `a == b` для объектов — **это один и тот же объект в памяти?** (как `is` в Python);
- `a.equals(b)` — **равны ли они по смыслу?** (как `==` в Python, то есть `__eq__`).

По умолчанию `equals` работает как `==`. Чтобы два `new Money(100, "RUB")` считались равными, `equals` надо переопределить.

**`hashCode`** — число, по которому `HashMap` и `HashSet` решают, в какую «корзину» положить объект. Правило (контракт):
**равные объекты обязаны иметь равные хеши.** Если переопределил `equals`, а `hashCode` забыл, `HashSet` будет считать
равные объекты разными: они попадут в разные корзины, и поиск не найдёт. Это прямой аналог правила `__eq__`/`__hash__` в Python.
Разница в том, что Python в этом случае просто сделает объект нехешируемым (ошибка сразу), а Java тихо сломается.

**`toString`** — текстовое представление для логов и отладки (как `__repr__`).

**Сравнение порядка:**
- `Comparable<T>` — «естественный» порядок, реализуется в самом классе (`compareTo`). Как `__lt__`.
- `Comparator<T>` — внешнее правило сравнения, можно иметь сколько угодно. Как `key=` в `sorted()`.

**Хорошая новость:** `record` (тема 8) генерирует `equals`, `hashCode` и `toString` сам. IDEA тоже умеет генерировать.

### Как в Python → как в Java

```python
people.sort(key=lambda p: (p.dept, -p.salary, p.name))
```

```java
people.sort(Comparator.comparing(Person::dept)
        .thenComparing(Person::salary, Comparator.reverseOrder())
        .thenComparing(Person::name));
```

### Пример: что будет без `hashCode`

```java
class Point {                            // equals переопределён, hashCode — НЕТ
    final int x, y;
    Point(int x, int y) { this.x = x; this.y = y; }
    @Override public boolean equals(Object o) {
        return o instanceof Point p && p.x == x && p.y == y;
    }
}

var set = new HashSet<Point>();
set.add(new Point(1, 2));
set.contains(new Point(1, 2));           // false! Хеши разные, HashSet ищет не в той корзине
```

Вторая ловушка: **изменяемый объект как ключ**. Положил объект в `HashSet`, потом поменял поле, от которого зависит
`hashCode`. Объект лежит в «старой» корзине, а ищется в «новой»: `contains` вернёт `false`, хотя объект внутри.

### Частые ошибки
- `equals` без `hashCode` (и наоборот).
- Сравнение объектов через `==`.
- Изменяемые поля в `equals/hashCode` у объектов, которые лежат в `HashSet`/служат ключами `HashMap`.
- `compareTo` через вычитание `a - b`: переполнение `int` на больших значениях. Используй `Integer.compare(a, b)`.

> 🎯 **Спросят на собесе:** Что будет, если переопределить `equals`, но не `hashCode`?
> **Ответ:** Два равных объекта будут иметь разные хеши, попадут в разные бакеты `HashMap`/`HashSet`: дубли в сете,
> `get` не находит ключ.

> 🎯 **Спросят на собесе:** Можно ли использовать изменяемый объект как ключ `HashMap`?
> **Ответ:** Технически да, но если после вставки изменить поля, участвующие в `hashCode`, объект «потеряется» в мапе.
> Ключи должны быть иммутабельными.

## Тема 4. Наследование, интерфейсы, абстрактные классы, полиморфизм

### Простыми словами

**Интерфейс** — это контракт: «объект умеет делать вот это». Никакого состояния, только сигнатуры методов
(плюс, с Java 8, `default`-методы с реализацией). Класс объявляет: `class Circle implements Shape`, и компилятор
проверяет, что все методы реализованы.

В Python ты привык к **утиной типизации**: «если у объекта есть метод `area()`, значит, это фигура». В Java так не
работает. Чтобы метод мог принять «что угодно с `area()`», нужен интерфейс `Shape`, и объект обязан явно его реализовать.
Ближайший аналог в Python — `typing.Protocol`, но в Java реализация всегда объявляется явно.

**Абстрактный класс** — класс-заготовка: может иметь поля и часть реализации, но создать его объект нельзя.
Используется, когда у близких по смыслу классов есть общее состояние и общий код.

**Главные отличия от Python:**
- **Нет множественного наследования классов.** `extends` — только один родитель. Интерфейсов — сколько угодно.
- **Перегрузка (overloading)** — несколько методов с одним именем и разными параметрами (`print(int)`, `print(String)`).
  В Python её нет.
- **Переопределение (overriding)** — наследник заменяет метод родителя. Аннотация `@Override` просит компилятор проверить,
  что ты действительно переопределяешь, а не опечатался в имени.

**`sealed` + `record` + pattern matching** (Java 17–21) — современный способ описать «фигура — это ровно круг,
квадрат или треугольник». Компилятор знает все варианты и проверяет, что `switch` обработал каждый.

### Пример: интерфейс + sealed + switch

```java
sealed interface Shape permits Circle, Square {}          // других реализаций не будет
record Circle(double radius) implements Shape {}
record Square(double side) implements Shape {}

static double area(Shape shape) {
    return switch (shape) {                                // pattern matching
        case Circle c -> Math.PI * c.radius() * c.radius();
        case Square s -> s.side() * s.side();
        // default не нужен: компилятор знает, что вариантов ровно два.
        // Добавишь Triangle в permits — этот switch перестанет компилироваться. Это ХОРОШО.
    };
}
```

Сравни с цепочкой `if (shape instanceof Circle) ... else if (shape instanceof Square) ...`: добавишь новую фигуру,
и компилятор промолчит, а программа тихо пойдёт в `else`.

### Композиция вместо наследования (кратко, подробно в [мостике М2](02-0-bridge-oop-design.md))

Наследование ради переиспользования кода — ловушка. `class Stack extends ArrayList` получит методы `add(index, ...)`,
`remove(index)`, и «стек» можно будет сломать. Правильно: `Stack` **содержит** `ArrayList` в приватном поле и открывает
только `push/pop/peek`. Наследуйся, только если это настоящее «является» (**is-a**) и наследник ведёт себя везде как родитель.

### Частые ошибки
- Наследование ради пары общих методов.
- Нет `@Override` — опечатка в имени метода создаёт новый метод вместо переопределения.
- `instanceof`-лестницы вместо полиморфизма.
- Интерфейс «на всё» с 20 методами: реализующим классам приходится писать заглушки.

> 🎯 **Спросят на собесе:** Абстрактный класс vs интерфейс — когда что?
> **Ответ:** Интерфейс — контракт/роль, класс может реализовать много интерфейсов. Абстрактный класс — общее состояние
> и частичная реализация для близких по сути наследников. По умолчанию выбирай интерфейс.

> 🎯 **Спросят на собесе:** Перегрузка vs переопределение?
> **Ответ:** Overloading — разные сигнатуры, выбор на этапе компиляции по статическим типам аргументов.
> Overriding — та же сигнатура в наследнике, выбор в рантайме по фактическому типу объекта.

## Тема 5. Исключения

### Простыми словами

Механика как в Python: `throw` = `raise`, `try/catch/finally` = `try/except/finally`. Два принципиальных отличия.

**1. Checked-исключения.** В Java исключения делятся на два вида:
- **Unchecked** — наследники `RuntimeException` (`IllegalArgumentException`, `NullPointerException`...).
  Ведут себя как в Python: бросай где угодно, лови где хочешь.
- **Checked** — остальные наследники `Exception` (`IOException`, `SQLException`...). **Компилятор заставляет** либо поймать
  их, либо объявить в сигнатуре метода: `void read() throws IOException`. Не сделал — код не скомпилируется.

Идея: checked — для ситуаций, которые вызывающий **может и должен** обработать (файл не найден — спросить другой путь).
Unchecked — для ошибок программиста (передал `null`, нарушил предусловие). На практике многие (и Spring) предпочитают
unchecked, а checked-исключения из библиотек **оборачивают** в свои.

**2. try-with-resources** — это `with` из Python:

```java
try (var reader = Files.newBufferedReader(path)) {   // reader закроется САМ, даже при исключении
    return reader.readLine();
}
```

Работает с любым объектом, реализующим `AutoCloseable` (аналог `__enter__/__exit__`).

**Трансляция исключений.** Низкоуровневое исключение (`SQLException`) не должно улетать в верхние слои: контроллер не обязан
знать про SQL. Ловишь и бросаешь своё, **передавая оригинал как причину** (`cause`), чтобы не потерять stack trace:

```java
try {
    ...
} catch (SQLException e) {
    throw new DataAccessException("Не удалось загрузить пользователя " + id, e);  // e — причина
}
```

### Частые ошибки
- `catch (Exception e) {}` — проглотить ошибку. Худшее, что можно сделать: баг становится невидимым.
- `e.printStackTrace()` вместо логгера.
- Новое исключение без `cause`: теряется исходная причина.
- Исключения для обычного потока управления (например, «не нашли — бросили, поймали, вернули дефолт»).
- `return` в `finally`.

> 🎯 **Спросят на собесе:** Checked vs unchecked — когда что?
> **Ответ:** Checked — для ситуаций, из которых вызывающий может разумно восстановиться (файл не найден). Unchecked —
> ошибки программирования и нарушения предусловий. Современная практика (Spring) склоняется к unchecked.

> 🎯 **Спросят на собесе:** Что будет, если в `finally` сделать `return`?
> **Ответ:** Он перетрёт и возвращаемое значение, и выброшенное исключение — исключение потеряется. Так делать нельзя.

📚 **Читать:**
- CJ1, гл. 7 «Exceptions, Assertions, and Logging»: иерархия, try-with-resources, suppressed. Раздел про `java.util.logging` пропусти, логирование будет через SLF4J.
- EJ, гл. 10 «Исключения», Items 69–77. Особенно Item 70 (checked vs unchecked), Item 73 (исключения, соответствующие уровню абстракции — **трансляция исключений, пригодится в проекте 3**), Item 77 (не игнорируйте исключения).
- EJ 9 (try-with-resources вместо try-finally).

### Упражнения
- **5.1.** Прочитай текстовый файл построчно и посчитай статистику: строки, слова, самое длинное слово.
  Ресурс закрывается через try-with-resources. Отдельный тест на несуществующий файл: какое исключение вылетает
  наружу из твоего метода и почему именно такое?
  *С чего начать:* `Files.newBufferedReader(Path, Charset)` или `Files.lines(Path)`. Для тестов используй `@TempDir` из JUnit.

  валюты не совпадают. Checked или unchecked? Общий родитель? Аргументируй в README.

## Тема 6. Коллекции

### Простыми словами

В Python три главные коллекции: `list`, `dict`, `set`. В Java так же, но у каждой несколько **реализаций** с разными
свойствами, и выбирать нужно осознанно. Код пишется через **интерфейс** (`List`, `Map`, `Set`), а реализация
выбирается при создании:

```java
List<String> names = new ArrayList<>();        // переменная — интерфейс, объект — реализация
Map<String, Integer> ages = new HashMap<>();
```

Если позже понадобится другая реализация, поменяется одна строка.

**Какую реализацию брать:**

| Нужно | Бери | Python-аналог | Почему |
|-------|------|---------------|--------|
| Список | `ArrayList` | `list` | почти всегда. `LinkedList` — почти никогда |
| Очередь/стек | `ArrayDeque` | `collections.deque` | быстрые операции с обоих концов |
| Уникальные элементы | `HashSet` | `set` | `contains` за O(1) |
| ...с порядком добавления | `LinkedHashSet` | — | |
| ...отсортированные | `TreeSet` | `sorted(set)` | O(log n), есть `first()`, `ceiling()`... |
| Словарь | `HashMap` | — | **порядок не гарантирован!** |
| ...с порядком добавления | `LinkedHashMap` | **`dict`** | Python-`dict` помнит порядок, `HashMap` нет |
| ...отсортированный по ключу | `TreeMap` | — | |
| Ключи — enum | `EnumMap` / `EnumSet` | — | самые быстрые |
| Очередь с приоритетом | `PriorityQueue` | `heapq` | |

**Сложность операций** — то, что спрашивают всегда. `ArrayList.get(i)` — O(1), `ArrayList.contains(x)` — O(n)
(перебор), `HashSet.contains(x)` — O(1), `TreeSet.contains(x)` — O(log n). Если в цикле много раз спрашиваешь
«есть ли элемент», нужен `Set`, а не `List`.

**Неизменяемые коллекции:** `List.of(1, 2, 3)`, `Map.of("a", 1)`, `List.copyOf(other)`. Попытка `add` → исключение.

**Удобные методы `Map`** — пригодятся постоянно:

```java
Map<String, Integer> counts = new HashMap<>();
for (String word : words) {
    counts.merge(word, 1, Integer::sum);          // как counts[word] = counts.get(word, 0) + 1
}
Map<String, List<String>> byLetter = new HashMap<>();
for (String word : words) {
    byLetter.computeIfAbsent(word.substring(0, 1), k -> new ArrayList<>()).add(word);   // как defaultdict(list)
}
int n = counts.getOrDefault("java", 0);           // как dict.get(key, default)
```

**Удаление во время обхода:**

```java
for (String s : list) {
    if (s.isEmpty()) list.remove(s);               // ОШИБКА: изменяем список не через итератор
}
list.removeIf(String::isEmpty);                    // правильно
```

Что именно случится в ошибочном варианте, зависит от того, **где** стоит удаляемый элемент (проверено на Java 21):
- `["", "a", "b"]` или `["a", "b", ""]` → `ConcurrentModificationException`;
- `["a", "", "b"]` (удаляется **предпоследний**) → исключения **нет**, цикл просто завершается раньше, и последний элемент
  **не проверяется**. Это хуже исключения: баг тихий.

Почему: итератор `ArrayList` проверяет счётчик изменений в `next()`, а `hasNext()` сравнивает только позицию с размером.
После удаления предпоследнего элемента позиция совпадает с новым размером, `hasNext()` возвращает `false`, и до проверки
в `next()` дело не доходит. Вывод: **никогда не изменяй коллекцию в for-each** — ни ради исключения, ни в надежде, что «пронесёт».

### Частые ошибки
- `LinkedList` «потому что быстрые вставки»: на практике медленнее почти всегда.
- `List.contains` в цикле (O(n²)) вместо `Set`.
- `list.remove(0)` у `ArrayList` в цикле: каждый раз сдвигается весь массив. Для очереди — `ArrayDeque.poll()`.
- Надежда на порядок в `HashMap`.
- Удаление из коллекции в цикле `for-each`.

> 🎯 **Спросят на собесе:** Как устроен `HashMap`? Что будет при коллизии?
> **Ответ:** Массив бакетов, индекс = hash ключа (с перемешиванием старших бит) & (n-1). Коллизии — связный список в бакете,
> при > 8 элементах (и таблице ≥ 64) он превращается в красно-чёрное дерево. При превышении load factor (0.75) — resize ×2 с перераспределением.

> 🎯 **Спросят на собесе:** `ArrayList` vs `LinkedList`?
> **Ответ:** `ArrayList` почти всегда: O(1) доступ по индексу, данные лежат в памяти подряд (cache-friendly), добавление в конец
> амортизированно O(1). `LinkedList` — O(n) доступ, огромный оверхед на узлы; даже вставка в середину на практике медленнее
> из-за поиска позиции. Для очереди/стека — `ArrayDeque`.
> **Типичная ошибка:** «LinkedList быстрее при вставках».

> 🎯 **Спросят на собесе:** Что такое `ConcurrentModificationException` и как удалить элементы при итерации?
> **Ответ:** fail-fast итератор видит структурное изменение коллекции не через него. Удалять через `Iterator.remove()` или `removeIf`.
> **Типичная ошибка:** считать, что исключение гарантировано. Javadoc прямо пишет, что fail-fast работает «по мере возможности»
> (best effort): при удалении предпоследнего элемента исключения не будет, а последний элемент будет пропущен.

## Тема 7. Generics

### Простыми словами

Generics — это параметры типов: `List<String>` — «список строк». Компилятор проверяет, что ты не положишь туда число,
и тебе не нужно приводить типы при чтении. В Python `list[str]` — только подсказка для mypy. В Java это
**проверяется всегда**, код с ошибкой не соберётся.

Свои generic-классы и методы пишутся так:

```java
class Box<T> {                        // T — параметр типа, как TypeVar
    private final T value;
    Box(T value) { this.value = value; }
    T get() { return value; }
}

static <T extends Comparable<T>> T maxOf(T a, T b) {    // bounded type: T умеет сравниваться
    return a.compareTo(b) >= 0 ? a : b;
}
```

**Стирание типов (type erasure).** После компиляции параметры типов **исчезают**: `List<String>` и `List<Integer>`
в рантайме — один и тот же класс `List`. Поэтому нельзя `new T()`, нельзя `new T[10]`, нельзя
`if (list instanceof List<String>)`. Компилятор проверил типы и «стёр» их, а в нужных местах вставил приведения.

**Wildcards `?`** — самое сложное в теме. Разберём на примере.

`List<Integer>` **не является** `List<Number>`, хотя `Integer` — это `Number`. Почему? Если бы являлся, можно было бы
передать список целых в метод, который принимает `List<Number>`, и тот положил бы туда `Double`. Список «целых»
сломался бы. Поэтому:

```java
double sum(List<? extends Number> numbers)   // «список ЧЕГО-ТО, что является Number»:
                                             // читать можно (всё — Number), добавлять нельзя
void fill(List<? super Integer> target)      // «список чего-то, что является ПРЕДКОМ Integer»:
                                             // класть Integer можно, читать — только как Object
```

Мнемоника **PECS — Producer Extends, Consumer Super**: если коллекция **отдаёт** тебе элементы (producer) — `extends`;
если **принимает** (consumer) — `super`.

### Частые ошибки
- Raw types (`List list = new ArrayList();` без `<...>`): отключают проверку, и ошибки вылезут в рантайме.
- Пытаться узнать `T` в рантайме.
- Слишком жёсткие сигнатуры (`List<Number>`), в которые не передать `List<Integer>`.

> 🎯 **Спросят на собесе:** Что такое PECS?
> **Ответ:** Producer Extends, Consumer Super. Если из коллекции читаем (она производит T) — `? extends T`,
> если пишем в неё (потребляет T) — `? super T`. Пример: `Collections.copy(List<? super T> dest, List<? extends T> src)`.

> 🎯 **Спросят на собесе:** Что такое type erasure?
> **Ответ:** Параметры типов существуют только при компиляции; в байткоде они заменяются на границу (`Object` или bound),
> компилятор вставляет касты. Поэтому `List<String>` и `List<Integer>` в рантайме — один класс.

📚 **Читать:**
- CJ1, гл. 8 «Generic Programming» — целиком, особенно разделы про wildcard-типы и ограничения, связанные со стиранием.
- EJ, гл. 5 «Обобщённое программирование»: Item 26 (не используйте raw types), Item 28 (списки вместо массивов), Item 31 (**PECS**), Item 33 (типобезопасные гетерогенные контейнеры).
- [Oracle Tutorial: Generics](https://docs.oracle.com/javase/tutorial/java/generics/) — разделы Wildcards и Type Erasure.

  потом сравни со стандартной сигнатурой
  `public static <T extends Object & Comparable<? super T>> T max(Collection<? extends T> coll)`
  и объясни в README каждый её кусок.

  `put(String.class, "x")`, `get(String.class)` возвращает `String` без приведения.

## Тема 8. Records, enum, Optional

### Простыми словами

**`record`** — короткий способ объявить неизменяемый класс данных. Одна строка вместо 50:

```java
record Book(String title, String author, int year) {
    Book {                                     // компактный конструктор — место для валидации
        if (year < 0) throw new IllegalArgumentException("year");
    }
}
var b = new Book("Dune", "Herbert", 1965);
b.title();                                     // геттер без "get"
// equals, hashCode, toString — сгенерированы по всем полям
```

Прямой аналог `@dataclass(frozen=True)`. Используй для DTO, value-объектов, результатов методов.
Ограничения: нельзя наследоваться от record, все поля `final`.

**`enum`** в Java намного мощнее Python-`Enum`: каждая константа — полноценный объект с полями, конструктором
и даже **своей реализацией методов**:

```java
enum Planet {
    MERCURY(3.303e+23, 2.4397e6),
    EARTH(5.976e+24, 6.37814e6);

    private final double mass, radius;
    Planet(double mass, double radius) { this.mass = mass; this.radius = radius; }
    double surfaceGravity() { return 6.67300E-11 * mass / (radius * radius); }
}

Planet.valueOf("EARTH");                      // по имени
Planet.values();                              // все константы
```

Используй `enum` вместо строк и `int`-констант для фиксированных наборов: статусы, типы, уровни.
Для мапы с ключами-enum есть быстрая `EnumMap`.

**`Optional<T>`** — коробка, в которой значение либо есть, либо нет. Нужна как **возвращаемый тип** методов вида
`findById`: вызывающий не может «забыть» про отсутствие, как с `null`.

```java
Optional<User> user = repository.findById(42);
String city = user.map(User::address)                // если есть — достать адрес
                  .map(Address::city)
                  .orElse("unknown");                // если чего-то нет по дороге — дефолт
User u = repository.findById(42)
                   .orElseThrow(() -> new NotFoundException(42));   // нет — ошибка
```

### Частые ошибки
- `optional.get()` без проверки — тот же NPE, только с другим названием.
- `if (opt.isPresent()) { x = opt.get(); }` вместо `map`/`orElse`/`ifPresent`.
- `Optional` в полях и параметрах методов.
- `orElse(expensiveCall())`: аргумент вычисляется **всегда**. Для дорогого дефолта — `orElseGet(() -> expensiveCall())`.
- Строки вместо enum: `status.equals("ACTIVE")`.

> 🎯 **Спросят на собесе:** `orElse` vs `orElseGet`?
> **Ответ:** Аргумент `orElse` вычисляется всегда, даже если значение есть. `orElseGet` принимает `Supplier`
> и вызывает его лениво. Для дорогих дефолтов — `orElseGet`.

> 🎯 **Спросят на собесе:** Почему `Optional` не стоит делать полем или параметром метода?
> **Ответ:** Он не `Serializable`, добавляет аллокацию, а для параметров перегрузка или `null`-контракт яснее.
> `Optional` задуман как тип возврата «значения может не быть».

## Тема 9. Лямбды и Stream API

### Простыми словами

**Лямбда** — короткая анонимная функция, как `lambda` в Python, только может быть многострочной:
`x -> x * 2`, `(a, b) -> a + b`, `s -> { log(s); return s.trim(); }`.

В Java нет «типа функция», поэтому лямбда всегда реализует какой-то **функциональный интерфейс** —
интерфейс с одним абстрактным методом. Стандартные, которые нужно знать:

| Интерфейс | Метод | Смысл | Пример |
|-----------|-------|-------|--------|
| `Function<T,R>` | `R apply(T)` | превратить T в R | `s -> s.length()` |
| `Predicate<T>` | `boolean test(T)` | проверить условие | `s -> s.isEmpty()` |
| `Consumer<T>` | `void accept(T)` | что-то сделать с T | `s -> System.out.println(s)` |
| `Supplier<T>` | `T get()` | выдать значение | `() -> new ArrayList<>()` |
| `BiFunction<T,U,R>` | `R apply(T,U)` | из двух в одно | `(a, b) -> a + b` |

**Ссылка на метод** — ещё короче: `String::length` вместо `s -> s.length()`, `System.out::println`.

Лямбда может читать локальные переменные снаружи, но **не может их менять**: они должны быть effectively final
(не переприсваиваться). Это защита от ошибок при многопоточности.

**Stream API** — конвейер обработки коллекций. Похоже на генераторные выражения + `itertools`:

```python
# Python
result = sorted({o.customer for o in orders if o.paid})
```
```java
// Java
List<String> result = orders.stream()
        .filter(Order::paid)              // промежуточная операция — ленивая
        .map(Order::customer)
        .distinct()
        .sorted()
        .toList();                        // терминальная — запускает весь конвейер
```

Важно понимать:
- **Ленивость.** Пока не вызвана терминальная операция (`toList`, `count`, `forEach`, `collect`...), ничего не выполняется.
- **Одноразовость.** Стрим нельзя использовать дважды.
- **`Collectors`** — сборка результата: `groupingBy` (как `itertools.groupby`, только правильно), `partitioningBy`
  (разбить на true/false), `toMap`, `joining`.

```java
Map<String, Long> ordersPerCustomer = orders.stream()
        .collect(Collectors.groupingBy(Order::customer, Collectors.counting()));
```

**Стрим — не всегда лучше цикла.** Если цепочка на 10 строк с вложенными лямбдами, обычный `for` читается лучше.

### Частые ошибки
- `Collectors.toMap` на данных с дублирующимися ключами → `IllegalStateException`. Нужен третий аргумент (merge-функция).
- Побочные эффекты в `map`/`filter` (изменение внешних коллекций).
- `collect(Collectors.toList())` вместо `toList()` (Java 16+).
- `.filter(...).findFirst().isPresent()` вместо `.anyMatch(...)`.
- `parallelStream()` «для скорости»: почти всегда медленнее и опаснее.

> 🎯 **Спросят на собесе:** Промежуточные vs терминальные операции? Что такое ленивость стрима?
> **Ответ:** Промежуточные (`map`, `filter`) возвращают стрим и ничего не выполняют; терминальная (`collect`, `forEach`,
> `count`) запускает конвейер. Элементы обрабатываются поштучно через всю цепочку, возможен short-circuit (`findFirst`, `anyMatch`).

## Тема 10. Строки, ввод-вывод, время

### Простыми словами

**Строки.** `String` в Java неизменяема, как и в Python. Каждая «модификация» создаёт новую строку. Поэтому
складывать строки в цикле через `+` — это O(n²): на каждой итерации копируется всё накопленное. Решение —
`StringBuilder` (аналог сбора кусков в список и `"".join(...)`):

```java
var sb = new StringBuilder();
for (var row : rows) sb.append(row).append('\n');
String result = sb.toString();
// или проще, если есть коллекция: String.join("\n", rows)
```

Удобные вещи: text blocks (многострочные строки, как `"""` в Python), `"Hi %s".formatted(name)` (как f-string, но
через формат), `strip()`, `isBlank()`, `repeat(n)`, `lines()`.

**Файлы.** Современный API — `java.nio.file`: класс `Path` (как `pathlib.Path`) и утилиты `Files`:
`Files.readAllLines(path)`, `Files.writeString(path, text)`, `Files.lines(path)`. Эти методы `Files` всегда работают
в UTF-8. А вот там, где байты превращаются в символы (`new InputStreamReader(in)`, `new Scanner(in)`, `new String(bytes)`),
**указывай кодировку явно**: `StandardCharsets.UTF_8`. С Java 18 кодировка по умолчанию и так UTF-8 на всех системах
(JEP 400), но явное указание делает код однозначным и не зависящим от настроек JVM. Старые статьи с кракозябрами
в кириллице — как раз из времён, когда кодировка по умолчанию зависела от ОС.

**Время** — пакет `java.time`, аналог `datetime`, но строже:
- `Instant` — точный момент на временной шкале (UTC). Для «когда произошло событие».
- `LocalDate` / `LocalDateTime` — дата / дата-время «как на часах», **без часового пояса**. Для дня рождения, расписания.
- `ZonedDateTime` — дата-время с часовым поясом.
- `Duration` / `Period` — промежуток времени / дат.
- `Clock` — источник «текущего времени». Если класс берёт время из переданного `Clock`, а не вызывает `Instant.now()`
  напрямую, в тестах можно подставить фиксированное время. Это очень пригодится в проектах 5 и 7.

### Частые ошибки
- `+` для строк в цикле.
- Чтение файла без указания кодировки.
- `LocalDateTime` для моментов событий на сервере (неоднозначно при смене часового пояса).
- `Instant.now()` внутри бизнес-логики: время не подменить в тестах.

> 🎯 **Спросят на собесе:** Почему `String` иммутабелен?
> **Ответ:** Безопасность (пути, URL, ключи в мапах), кеширование `hashCode`, string pool, потокобезопасность.

> 🎯 **Спросят на собесе:** `LocalDateTime` vs `Instant`?
> **Ответ:** `Instant` — точка на временной шкале (UTC), для хранения моментов событий. `LocalDateTime` — дата-время без зоны,
> «как на часах», не определяет момент однозначно.

- CJ1, гл. 3, разделы Strings и Input and Output.
- CJ2, гл. 2 «Input and Output»: `Path`, `Files`, кодировки. Разделы про сериализацию и regex пропусти.

## Тема 11. Тестирование: JUnit + AssertJ

### Простыми словами

**JUnit** — стандарт тестов в Java (как pytest). Мы берём JUnit 6; его API (Jupiter) такой же, как у JUnit 5,
поэтому любые материалы по JUnit 5 подходят. Тест — метод с аннотацией `@Test` в классе из `src/test/java`.
**AssertJ** — библиотека читаемых проверок: `assertThat(x).isEqualTo(5)` вместо голого `assert`.

```java
class ThermometerTest {                                   // имя: <Класс>Test

    @Test
    void toFahrenheit_zeroCelsius_returns32() {           // метод_условие_результат
        // Arrange — подготовка
        var t = Temperature.celsius(0);
        // Act — действие
        double f = t.toFahrenheit();
        // Assert — проверка
        assertThat(f).isEqualTo(32.0);
    }

    @Test
    void celsius_belowAbsoluteZero_throws() {
        assertThatThrownBy(() -> Temperature.celsius(-300))
                .isInstanceOf(IllegalArgumentException.class)
                .hasMessageContaining("absolute zero");
    }

    @ParameterizedTest                                    // как @pytest.mark.parametrize
    @CsvSource({"0, true", "5, false", "-1, false"})
    void isZero(int value, boolean expected) {
        assertThat(value == 0).isEqualTo(expected);
    }
}
```

Что ещё пригодится: `@BeforeEach` (как фикстура, вызывается перед каждым тестом), `@Nested` (группы тестов внутри класса),
`@DisplayName` (читаемое имя), `@TempDir` (временная папка), `@MethodSource` (параметры из метода).

AssertJ для коллекций: `assertThat(list).containsExactly("a", "b")`, `.hasSize(2)`, `.extracting(User::name)`.
Для `BigDecimal` — `isEqualByComparingTo(...)` (почему — в проекте 3).

### Частые ошибки
- Тест без ассертов («не упал — значит работает»).
- Несколько несвязанных проверок в одном тесте.
- Тесты, зависящие от порядка запуска или друг от друга.
- Проверка только «счастливого пути», без граничных случаев.

📚 **Читать:**
- [JUnit User Guide](https://docs.junit.org/current/user-guide/): разделы Writing Tests, Parameterized Tests, Nested Tests.
- [AssertJ: Core features](https://assertj.github.io/doc/#assertj-core-assertions-guide) — пролистай, какие бывают ассерты.
- UTPP, гл. 3 «The anatomy of a unit test» (AAA, именование тестов) — по диагонали.
