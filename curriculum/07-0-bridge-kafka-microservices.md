# Мостик М7. Микросервисы, Kafka, JWT

**Зачем мостик.** Последний проект — четыре сервиса, общающихся через брокер сообщений Kafka, stateless-аутентификация
на JWT, сборка Docker-образов и CI/CD. Это другой способ думать о системе: вместо «вызвал метод — получил ответ»
появляются «отправил сообщение — когда-нибудь обработают, возможно дважды». Здесь разбираем идеи и пробуем Kafka на игрушке.

**Как проходить.** Песочница `projects/07-0-bridge/`: два маленьких Boot-приложения (продюсер и консьюмер) + compose с Kafka,
потом JWT на отдельном мини-приложении.

**Сколько времени:** 7–10 дней.

## Часть 1. Монолит и микросервисы

### Простыми словами

**Монолит** — одно приложение, один деплой, одна БД. Все проекты 1–6 — монолиты. Плюсы: просто разрабатывать, отлаживать,
деплоить; вызов модуля — обычный вызов метода; транзакция покрывает всё.

**Микросервисы** — несколько независимых приложений, у каждого своя ответственность и (в идеале) **своя БД**.
Общаются по сети: синхронно (HTTP) или асинхронно (через брокер сообщений).
Плюсы: независимый деплой и масштабирование частей, изоляция отказов, разные команды над разными сервисами.
Цена: сеть ненадёжна (таймауты, повторы), **нет общей транзакции**, данные дублируются, сложнее отладка
(запрос проходит через 3 сервиса — где ошибка?), нужна инфраструктура (брокер, мониторинг, трейсинг).

**Честная позиция:** для маленького проекта микросервисы — избыточны. В проекте 7 они учебные: ты почувствуешь их цену,
чтобы на работе понимать, когда они оправданы.

**Database per service.** Если два сервиса пишут в одни таблицы, они намертво связаны: поменял схему — сломал соседа.
Правило: у данных один владелец; остальные получают их через API или события.

## Часть 2. Брокер сообщений и Kafka

### Простыми словами

**Синхронно (HTTP):** сервис A вызывает B и ждёт ответа. Если B лежит — A тоже не может работать.

**Асинхронно (брокер):** A кладёт сообщение в брокер и идёт дальше. B заберёт его, когда сможет. B лежит час — сообщения
подождут. Аналогия: почтовый ящик вместо телефонного звонка. В Python-мире ты мог встречать Celery + RabbitMQ/Redis.

**Kafka** — брокер, устроенный как **журнал (лог)** сообщений:
- **Топик (topic)** — именованный журнал сообщений, например `EMAIL_SENDING_TASKS`.
- **Партиция (partition)** — топик разбит на части для параллелизма. Внутри партиции сообщения строго упорядочены.
- **Offset** — порядковый номер сообщения в партиции. Сообщения **не удаляются при чтении** (хранятся по retention),
  каждый читатель сам помнит, до какого offset дочитал.
- **Продюсер (producer)** — пишет сообщения. У сообщения может быть **ключ**: сообщения с одинаковым ключом попадают
  в одну партицию, значит, обрабатываются по порядку.
- **Консьюмер (consumer)** и **consumer group** — читатели. Внутри одной группы каждая партиция достаётся ровно одному
  консьюмеру (так делится работа). Разные группы читают топик независимо (каждая получает все сообщения).

```
Топик orders (3 партиции)            Consumer group "billing"      Consumer group "email"
  P0: [m0][m3][m6] ...  ────────>      consumer-1 (P0, P1)         consumer-A (P0, P1, P2)
  P1: [m1][m4][m7] ...  ────────>      consumer-2 (P2)
  P2: [m2][m5][m8] ...  ────────>
```

> 🎯 **Спросят на собесе:** Как Kafka гарантирует порядок сообщений?
> **Ответ:** Только внутри партиции. Сообщения с одинаковым ключом попадают в одну партицию (hash ключа), поэтому для
> упорядоченной обработки по сущности (пользователь, заказ) используют её ID как ключ. Между партициями порядка нет.

> 🎯 **Спросят на собесе:** Что такое consumer group?
> **Ответ:** Набор консьюмеров, делящих партиции топика: каждая партиция читается ровно одним консьюмером группы.
> Разные группы читают топик независимо (каждая со своими offset'ами). Если консьюмеров больше, чем партиций, лишние простаивают.

### Семантики доставки и идемпотентность

Консьюмер прочитал сообщение, обработал (отправил письмо) и должен **закоммитить offset** («я дочитал до сюда»).
Что если упал между «отправил письмо» и «закоммитил»? После рестарта он прочитает то же сообщение снова и отправит письмо **второй раз**.

- **At-most-once** — коммитим offset **до** обработки: при падении сообщение потеряется.
- **At-least-once** — коммитим **после**: при падении сообщение обработается повторно. **Стандарт**.
- **Exactly-once** — ровно один раз: сложно, возможно только в определённых сценариях (Kafka → Kafka).

Раз стандарт — at-least-once, **консьюмер обязан быть идемпотентным**: повторная обработка того же сообщения не должна
давать повторный эффект. Приём: у сообщения уникальный ID; консьюмер хранит ID обработанных (таблица с уникальным
ограничением) и пропускает уже виденные.

> 🎯 **Спросят на собесе:** Что такое идемпотентность и как сделать консьюмер идемпотентным?
> **Ответ:** Повторное выполнение операции даёт тот же результат, что и однократное. Для консьюмера: уникальный ID сообщения
> (или бизнес-ключ) + таблица обработанных ID с уникальным ограничением в той же транзакции, что и эффект; либо
> естественно идемпотентные операции (upsert, «установить статус X»).

### Ошибки обработки: retry и DLT

Сообщение не обрабатывается (битый JSON, баг). Если просто бросать исключение, консьюмер будет вечно перечитывать его
и застрянет («ядовитое сообщение»). Решение: несколько повторов с паузой, потом отправить сообщение в **Dead Letter Topic**
(DLT) для ручного разбора и идти дальше. В Spring Kafka это `DefaultErrorHandler` + `DeadLetterPublishingRecoverer`.

### Transactional Outbox

**Проблема.** Сервис регистрирует пользователя (запись в БД) и должен отправить в Kafka событие «пошли приветственное
письмо». Это две разные системы, общей транзакции нет:
- записал в БД, отправил в Kafka, транзакция БД откатилась → письмо ушло несуществующему пользователю;
- закоммитил БД, Kafka недоступна → пользователь есть, письма нет.

**Решение — Outbox.** В **той же транзакции**, что и пользователя, пишешь событие в таблицу `outbox`. Отдельный процесс
(поллер по расписанию или CDC — Debezium) читает `outbox`, отправляет в Kafka и помечает отправленные. Событие не потеряется
и не уйдёт без коммита. Возможны дубли (at-least-once) — их гасит идемпотентный консьюмер.

> 🎯 **Спросят на собесе:** Как надёжно записать в БД и отправить событие в Kafka?
> **Ответ:** Transactional Outbox: в той же транзакции, что и бизнес-изменение, пишем событие в таблицу `outbox`;
> отдельный процесс (поллер или CDC — Debezium) читает outbox и публикует в Kafka, помечая отправленные.
> Получается at-least-once, поэтому консьюмеры идемпотентны.
> **Типичная ошибка:** «отправить в Kafka внутри `@Transactional`» — если транзакция откатится после отправки, событие уже ушло.

### Request-Reply через Kafka

Иногда нужен ответ: планировщик просит сервис суммаризации сгенерировать отчёт и ждёт результат. Через брокер это делается
так: запрос уходит в топик запросов с **correlation ID** и адресом топика ответов; сервис отвечает в топик ответов с тем же
correlation ID; вызывающий сопоставляет ответ с запросом по ID и ждёт с **таймаутом**. В Spring Kafka есть `ReplyingKafkaTemplate`.

### Spring Kafka в двух фрагментах

```java
// Продюсер (нейтральный пример — события заказов)
@Service
class OrderEvents {
    private final KafkaTemplate<String, OrderPlaced> kafka;
    OrderEvents(KafkaTemplate<String, OrderPlaced> kafka) { this.kafka = kafka; }
    void publish(OrderPlaced event) {
        kafka.send("orders", event.orderId(), event);      // ключ = orderId → порядок по заказу
    }
}

// Консьюмер
@Component
class InvoiceListener {
    @KafkaListener(topics = "orders", groupId = "billing")
    void on(OrderPlaced event) { ... }                      // JSON → объект через JsonDeserializer
}
```

## Часть 3. JWT

### Простыми словами

В проектах 5–6 сервер хранил сессии: кука содержала ID, по ID сервер находил пользователя в БД/Redis. Это **stateful**.

**JWT (JSON Web Token)** — **stateless**-подход: сервер выдаёт клиенту токен, в котором **уже записано**, кто это
(id, email, срок годности), и **подписывает** его своим секретом. Клиент шлёт токен в заголовке
`Authorization: Bearer <token>`. Сервер проверяет подпись: совпала — данным в токене можно верить, в БД ходить не надо.

Токен — три части через точку, каждая в base64url: `header.payload.signature`.
- header: `{"alg":"HS256","typ":"JWT"}`;
- payload (claims): `{"sub":"42","email":"a@b.c","exp":1735689600}`;
- signature: подпись первых двух частей секретом.

**Важно:**
- Payload **не зашифрован**, его может прочитать кто угодно (вставь токен на jwt.io). Никаких паролей и секретов внутри.
- Подпись защищает от **подделки**, а не от чтения.
- Отозвать токен до истечения `exp` нельзя без хранения чёрного списка (то есть без состояния). Поэтому access-токены
  короткоживущие (минуты-часы), а для продления используют refresh-токены.
- Алгоритмы: **HS256** — один общий секрет (проще); **RS256** — пара ключей: подписывает один сервис приватным,
  проверяют все публичным (удобно для микросервисов).

**В Spring Security** JWT проверяется фильтром: свой `OncePerRequestFilter` (достать заголовок → проверить подпись и `exp` →
положить `Authentication` в `SecurityContextHolder`) или готовый Resource Server (`oauth2-resource-server` + `JwtDecoder`).
Сессии выключаются: `SessionCreationPolicy.STATELESS`.

> 🎯 **Спросят на собесе:** JWT vs сессии?
> **Ответ:** JWT — stateless, сервер не хранит состояние, легко масштабировать, подходит для межсервисного взаимодействия;
> но токен нельзя отозвать до `exp` без чёрного списка (т. е. без состояния), а payload виден всем.
> Сессии легко отозвать, но при масштабировании нужно общее хранилище.

## Часть 4. Dockerfile и CI/CD — коротко

**Dockerfile** — рецепт сборки своего образа. **Multi-stage**: первая стадия на образе с JDK и Maven собирает JAR,
вторая на лёгком образе с JRE копирует только JAR. В итоговом образе нет ни исходников, ни Maven, ни JDK.

```dockerfile
FROM eclipse-temurin:21-jdk AS build        # стадия сборки
WORKDIR /src
COPY . .
RUN ./mvnw -q package -DskipTests

FROM eclipse-temurin:21-jre                 # финальный образ — только JRE
RUN useradd -r app
USER app                                    # не root
COPY --from=build /src/target/app.jar /app.jar
ENTRYPOINT ["java", "-jar", "/app.jar"]
```

**CI/CD (GitHub Actions)** — YAML-файл в `.github/workflows/`: на каждый push GitHub запускает виртуалку, выполняет шаги
(checkout → тесты → сборка образа → push в Docker Hub). Секреты (пароль Docker Hub) — в *Settings → Secrets* репозитория,
в YAML доступны как `${{ secrets.NAME }}`.

## Упражнения и вехи

### Веха B7.1 — Kafka

**Что нужно сделать**
1. Compose с Kafka (официальный образ `apache/kafka`, режим KRaft — в Kafka 4 другого и нет) + веб-интерфейс
   `ghcr.io/kafbat/kafka-ui` ([kafbat/kafka-ui](https://github.com/kafbat/kafka-ui)).
   ⚠️ Старые туториалы используют `bitnami/kafka` и `provectuslabs/kafka-ui`: бесплатный каталог Bitnami с 2025 года урезан,
   а `provectuslabs/kafka-ui` больше не развивается (его продолжение — `kafbat`).
2. Boot-продюсер: `POST /orders` публикует событие `OrderPlaced` (JSON, ключ = orderId) в топик с 3 партициями.
3. Boot-консьюмер (отдельное приложение): логирует события. Запусти **два экземпляра** в одной группе — посмотри в UI,
   как поделились партиции. Потом запусти третий экземпляр в **другой** группе — он получает все сообщения.
4. **Дубли своими глазами:** консьюмер падает (бросает исключение) после «обработки», но до коммита; убедись, что сообщение
   обработается повторно. Сделай консьюмер идемпотентным (хранит обработанные ID в Postgres с `UNIQUE`).
5. **Ядовитое сообщение:** отправь битый JSON; настрой retry (3 попытки) + DLT; убедись, что консьюмер не застрял.

**С чего начать.** С п. 1–2 и kafka-ui: увидеть своё первое сообщение в топике глазами.

**Как проверить себя**
- [ ] Можешь объяснить, почему два консьюмера одной группы не получают одно сообщение дважды, а разные группы получают.
- [ ] Повторная доставка не создаёт повторного эффекта.
- [ ] Битое сообщение оказалось в DLT, обработка продолжилась.
