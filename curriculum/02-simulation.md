# Проект 2. Симуляция

**ТЗ:** [zhukovsd — Симуляция](https://zhukovsd.github.io/java-backend-learning-course/projects/simulation/)

Пошаговая симуляция 2D-мира. На карте: трава, камни, деревья, травоядные, хищники. Травоядные идут к траве и едят её.
Хищники идут к травоядным и атакуют их. Каждый ход мир перерисовывается в консоли.

В ТЗ уже дан **скелет** дизайна:
- `Entity` — корень всех объектов на карте; `Grass`, `Rock`, `Tree` — статичные объекты;
- `Creature extends Entity` — существо со скоростью и HP и методом `makeMove()`; `Herbivore`, `Predator` — его наследники;
- `Map` — хранит, что где стоит;
- `Simulation` — карта + счётчик ходов + рендерер + списки действий; методы `nextTurn()`, `startSimulation()`, `pauseSimulation()`;
- `Action` — действие над миром: `initActions` (один раз при старте, например расставить объекты) и `turnActions` (каждый ход);
- поиск пути — BFS, потом A*; рендерер — рисует карту.

Это главный ООП-проект роадмапа. Перед ним **обязательно** пройди [мостик М2](02-0-bridge-oop-design.md):
здесь используется всё оттуда.

**Сколько времени:** 2–3 недели.

## Что изучить до старта

Паттерны, SOLID, композиция и потоки разобраны в [мостике М2](02-0-bridge-oop-design.md). Здесь — то, что

### 1. Координата как Value Object

**Простыми словами.** Координата `(x, y)` — классический **value object**: объект, который определяется значением.
Две координаты `(3, 5)` — одна и та же координата, даже если это два разных объекта в памяти. У value object должны
быть правильные `equals`/`hashCode`, и он должен быть неизменяемым.

Почему неизменяемым: если координата — ключ в `HashMap`, а потом её поля изменят, объект «потеряется»
(вспомни тему 3 модуля 0′). В Java 16+ идеальный кандидат — `record`: `equals/hashCode` сгенерированы, поля `final`.

```java
record Point(int x, int y) {
    Point shift(int dx, int dy) { return new Point(x + dx, y + dy); }   // «сдвиг» = новый объект
}
var m = new HashMap<Point, String>();
m.put(new Point(1, 2), "tree");
m.get(new Point(1, 2));   // "tree" — работает, потому что record сравнивается по значению
```

### 2. Как хранить карту

**Простыми словами.** Первая мысль — двумерный массив `Entity[][]`. В ТЗ прямо советуют не спешить с ним. Подумай:
- на карте 20×20 = 400 клеток, а объектов, может, 40. Массив хранит 360 пустот, и их везде придётся обходить (`if (cell != null)`);
- частый вопрос «где все травоядные?» с массивом — перебор всех 400 клеток;
- размер массива фиксирован.

Альтернатива — хранить **только занятые клетки**: мапа «координата → сущность». Какая мапа и почему — реши сам,
исходя из операций, которые понадобятся (см. вопросы вехи 2.1).

**Инкапсуляция карты** — самое важное в этом классе. Снаружи не должно быть видно, **как** хранится мир.
Карта даёт методы с говорящими названиями, а не свою внутреннюю коллекцию:

```java
// ПЛОХО: наружу торчит внутренность — любой может сломать инварианты
public Map<Point, Entity> getCells() { return cells; }

// ЛУЧШЕ (нейтральный пример — склад): операции предметной области
class Warehouse {
    private final Map<Slot, Box> slots = new HashMap<>();
    public void place(Slot s, Box b) { if (slots.containsKey(s)) throw ...; slots.put(s, b); }
    public Optional<Box> boxAt(Slot s) { return Optional.ofNullable(slots.get(s)); }
    public boolean isFree(Slot s) { return !slots.containsKey(s); }
    public void remove(Slot s) { ... }
}
```

### 3. Типобезопасный поиск «всех сущностей типа X»

**Простыми словами.** Хищнику нужны травоядные, травоядному — трава. Можно написать `getHerbivores()`, `getGrass()`, ...
но это копипаста, и каждый новый тип потребует нового метода. Лучше один generic-метод, который принимает **класс**
и возвращает список нужного типа без приведений снаружи:

```java
// Нейтральный пример: из списка животных выбрать всех, кто является экземпляром clazz
<T extends Animal> List<T> allOf(Class<T> clazz) {
    return animals.stream()
            .filter(clazz::isInstance)        // «является ли экземпляром clazz?»
            .map(clazz::cast)                 // безопасное приведение
            .toList();
}
List<Cat> cats = zoo.allOf(Cat.class);        // без (Cat) снаружи
```

`Class<T>` — объект, описывающий класс в рантайме. `Cat.class` — литерал, дающий такой объект.

### 4. Поиск в ширину (BFS)

**Простыми словами.** Нужно найти кратчайший путь по клеткам от существа до ближайшей цели, обходя препятствия.
BFS — «волна» от стартовой клетки:
1. Кладёшь старт в **очередь**, помечаешь посещённым.
2. Пока очередь не пуста: достаёшь клетку; если это цель — готово. Иначе кладёшь в очередь всех ещё не посещённых
   проходимых соседей и для каждого запоминаешь, **откуда пришёл** (родителя).
3. Когда нашёл цель — идёшь по родителям назад до старта. Это и есть путь (в обратном порядке).

Волна расходится равномерно, поэтому первая найденная цель — **ближайшая** (в сетке без весов).

Нужные структуры: очередь — `ArrayDeque` (`offer`/`poll`), посещённые — `Set`, родители — `Map<клетка, клетка>`.

**Как BFS выглядит на совсем другой задаче** — поиск минимального числа «рукопожатий» между людьми в соцсети:

```java
Optional<List<Person>> chain(Person from, Person to) {
    Deque<Person> queue = new ArrayDeque<>(List.of(from));
    Map<Person, Person> parent = new HashMap<>();
    Set<Person> seen = new HashSet<>(Set.of(from));
    while (!queue.isEmpty()) {
        Person cur = queue.poll();
        if (cur.equals(to)) return Optional.of(restore(parent, to));    // пройти по parent назад
        for (Person friend : cur.friends()) {
            if (seen.add(friend)) { parent.put(friend, cur); queue.offer(friend); }
        }
    }
    return Optional.empty();                                           // недостижимо
}
```

Твоя задача — перенести **идею** на клетки карты: кто «соседи», что «проходимо», что «цель».

**A\*** — улучшенный поиск: вместо равномерной волны сначала проверяет клетки, которые **ближе к цели по прямой**
(эвристика). Посещает меньше клеток. Вместо очереди — `PriorityQueue`. Отличное объяснение с картинками:
[Red Blob Games](https://www.redblobgames.com/pathfinding/a-star/introduction.html).

## Паттерны и принципы в фокусе

- **Template Method** — ход существа: каркас общий (найти цель → если рядом, взаимодействовать, иначе идти),
  шаги разные. Где проходит граница между общим и частным?
- **Strategy** — поиск пути (BFS/A* взаимозаменяемы). Поиск пути **не живёт внутри существ**: так прямо сказано в чеклисте курса.
- **Command** — `Action`: каждое действие над миром — объект; `Simulation` не знает конкретных действий.
- **Factory** — создание существ с параметрами из диапазонов.
- **Observer** (опционально) — рендерер или статистика подписаны на события хода.
- **OCP** — новый вид существ не должен требовать правки `Map`, `Simulation`, рендерера (кроме, может быть, регистрации символа).
- **LSP** — `Rock` — это `Entity`, но не `Creature`. Не должно быть `makeMove()`, который у камня бросает исключение.
- **Инкапсуляция `Map`** — наружу методы, а не коллекция.

### Веха 2.2 — Рендерер

**Что нужно сделать.** Класс, который по карте печатает кадр: каждая клетка — символ или эмодзи (🌿 🪨 🌳 🐇 🐺, пустая — `..`).

**С чего начать.** Подумай, где должна жить информация «какой символ у травы»: в классе `Grass` (модель) или
в рендерере (представление)? Вспомни раздел про модель/представление из Виселицы.

**Вопросы для размышления**
1. Как сопоставить тип сущности и символ **без** цепочки `instanceof`?
   *Направление: варианты — `Map<Class<?>, String>` в рендерере, метод у сущности, `switch` по `sealed`-иерархии.
   У каждого свои плюсы. Какой лучше соблюдает разделение модели и представления? Какой заставит компилятор напомнить
   о новом виде существа?*
2. Как собрать кадр 20×20 эффективно? *Направление: тема 10 модуля 0′.*

**Как проверить себя**
- [ ] Рендерер знает о карте только через её публичные методы.
- [ ] Нет `instanceof`-лестницы.
- [ ] Кадр собирается через `StringBuilder`, не `+` в цикле.
- [ ] Выбор способа сопоставления тип → символ обоснован в README.

### Веха 2.3 — Actions и цикл симуляции

**Что нужно сделать**
1. Контракт действия и несколько реализаций: расставить объекты каждого вида (init), сходить всеми существами (turn),
   подсыпать траву/травоядных, если их мало (turn).
2. `Simulation` с `nextTurn()`: при первом ходе один раз выполнить `initActions`, затем на каждом ходе `turnActions`,
   увеличить счётчик, отрисовать.

**С чего начать.** Опиши интерфейс `Action` одной строкой. Потом сделай **одно** действие «расставить N объектов
типа X» — так, чтобы его можно было переиспользовать для травы, камней, деревьев и существ.

**Вопросы для размышления**
1. Как избежать копипасты «поставить N травы», «поставить N камней»...?
   *Направление: что отличается между ними? Только «кого создавать» и «сколько». Как передать «кого создавать»?
   Вспомни `Supplier` из темы 9 модуля 0′ и Factory из мостика.*
2. «Подсыпать траву, если её мало» — это отдельное действие или то же «расставить»? Как переиспользовать?
3. Существо переместилось на клетку, которую ещё предстоит обойти в этом же ходу. Как не дать ему сходить дважды?
   *Направление: по какой коллекции ты итерируешь — по «живой» карте или по снимку списка существ на начало хода?*

**Как проверить себя**
- [ ] `Simulation` получает списки действий снаружи (или собирает в одном месте) и не знает конкретных классов действий.
- [ ] Нет `ConcurrentModificationException` при перемещении/удалении во время хода, и нет `try/catch` вокруг как «лекарства».
- [ ] Действия расстановки не дублируют код друг друга.

### Веха 2.4 — Поиск пути (BFS)

**Что нужно сделать.** Отдельный класс поиска пути за интерфейсом: от клетки до ближайшей цели, обходя препятствия.
Юнит-тесты на маленьких картах.

**С чего начать.** Опиши интерфейс: что на вход (карта, старт, как понять «это цель»), что на выход (путь? следующая клетка?
пустой результат, если пути нет?). Потом нарисуй на бумаге карту 5×5 и пройди BFS руками по шагам из раздела 4.

**Вопросы для размышления**
1. Как одним алгоритмом обслужить и хищника (цель — травоядное), и травоядное (цель — трава)?
   *Направление: передай «что является целью» параметром — `Predicate`, `Class<T>`...*
2. Что считать проходимым? Цель ведь тоже занятая клетка.
3. Что вернуть, если пути нет? *Направление: тема 8 модуля 0′.*

**Как проверить себя**
- [ ] Поиск пути — отдельный класс за интерфейсом, существа зависят от интерфейса.
- [ ] Один алгоритм для всех существ, без копипасты.
- [ ] Тесты: цель рядом; прямой путь; обход препятствия; цели нет; цель недостижима (окружена камнями).

### Веха 2.5 — Поведение существ

**Что нужно сделать.** `makeMove()`: травоядное идёт к траве (за ход — до `speed` клеток) или ест её, если рядом;
хищник идёт к травоядному или атакует (HP жертвы −= сила атаки; HP ≤ 0 → жертва исчезает).

**С чего начать.** Опиши словами общий алгоритм хода, одинаковый для обоих видов, и выдели шаги, которые отличаются.
Это твой Template Method (мостик М2, часть 3).

**Вопросы для размышления**
1. Как существо узнаёт, где еда, если поиск пути — отдельный класс? Кто кому передаётся?
   *Направление: через конструктор (DI) или параметром `makeMove(map)`. Что лучше тестируется?*
2. Где задаются диапазоны HP/скорости/атаки, чтобы менять баланс в одном месте?

**Как проверить себя**
- [ ] Общий каркас хода — в `Creature`, различия — в наследниках (или стратегиях). Копипасты нет.
- [ ] Параметры баланса в одном месте (константы/конфиг).
- [ ] Смерть корректно убирает существо с карты.
- [ ] Тест: хищник рядом с травоядным атакует; травоядное рядом с травой ест.

### Веха 2.6 — Бесконечный цикл и пауза

**Что нужно сделать.** `startSimulation()` крутит ходы в отдельном потоке с задержкой между кадрами; с клавиатуры
можно поставить на паузу, продолжить и выйти.

**С чего начать.** Перечитай [мостик М2, часть 5](02-0-bridge-oop-design.md#часть-5-потоки-минимум-для-симуляции)
и своё решение вехи B2.2: там ты уже делал ровно эту механику на «тикере».

**Вопросы для размышления**
