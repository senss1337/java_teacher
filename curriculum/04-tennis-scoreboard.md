# Проект 4. Табло теннисного матча

**ТЗ:** [zhukovsd — Табло теннисного матча](https://zhukovsd.github.io/java-backend-learning-course/projects/tennis-scoreboard/)

REST API для ведения счёта теннисного матча:
- `POST /matches` — создать матч по именам двух игроков, в ответ UUID;
- `POST /matches/{uuid}/point` — начислить очко игроку, в ответ текущий счёт;
- `GET /matches/{uuid}` — текущий счёт;
- `GET /matches?page=&player_name=` — завершённые матчи с пагинацией и поиском по имени.

Текущие матчи хранятся **в памяти** (в потокобезопасной коллекции), завершённые — в Postgres через **Hibernate**.
Стек: Spring MVC 7 (без Boot), Hibernate 7, Postgres, JUnit, деплой WAR в Tomcat 11
(версии — по таблице [«Версии стека»](00-setup.md#7-версии-стека-проверено-по-maven-central-24092026)).
Есть [фронтенд](https://github.com/zhukovsd/tennis-scoreboard-frontend): статические файлы кладутся в проект.

Перед проектом **обязательно** пройди [мостик М4](04-0-bridge-spring-hibernate.md): Spring, прокси, Hibernate,
состояния сущности, N+1.

**Сколько времени:** 3–4 недели.

## Что изучить до старта

### 1. Правила тенниса (упрощённые по ТЗ)

Разберись с ними **до** кода: половина багов проекта — непонимание правил.
- **Очки в гейме:** 0 → 15 → 30 → 40 → гейм. Названия: love, fifteen, thirty, forty.
- **«Больше-меньше» (deuce/advantage):** при 40:40 нужно выиграть **два очка подряд**. Выиграл одно → «преимущество» (AD).
  Выиграл следующее → гейм; проиграл → снова 40:40.
- **Сет:** до 6 геймов с разницей в 2 (6:4, 7:5). При **6:6** играется **тай-брейк**.
- **Тай-брейк:** очки считаются числами 1, 2, 3...; до 7 с разницей в 2 (7:5, 8:6, 12:10).
- **Матч:** до двух выигранных сетов (best of 3).

Ссылка из ТЗ: [правила на gotennis.ru](https://www.gotennis.ru/read/world_of_tennis/pravila.html).

### 2. Богатая vs анемичная доменная модель

**Простыми словами.** Есть два способа разместить бизнес-логику:
- **Анемичная модель + Transaction Script:** классы-модели — просто данные с геттерами/сеттерами, вся логика в сервисе.
  Для CRUD нормально (проект 3 так и выглядел). Но если логика сложная, сервис распухает до сотен строк с `if`,
  и любой код может записать в модель что угодно через сеттеры.
- **Богатая модель (Domain Model):** логика живёт **внутри** объектов, рядом с данными, которые она меняет.
  Объект сам защищает свои правила. Сервис только достаёт объект, говорит ему «сделай» и сохраняет результат.

```java
// АНЕМИЧНО: заказ — мешок данных, правила снаружи
class Order { List<Item> items; Status status; /* геттеры/сеттеры */ }
class OrderService {
    void ship(Order o) {
        if (o.getStatus() != Status.PAID) throw ...;       // правило в сервисе
        if (o.getItems().isEmpty()) throw ...;
        o.setStatus(Status.SHIPPED);                        // а кто-то другой может вызвать setStatus в обход проверок
    }
}

// БОГАТО: заказ сам знает свои правила
class Order {
    private final List<Item> items = new ArrayList<>();
    private Status status = Status.NEW;

    void addItem(Item i) { requireStatus(Status.NEW); items.add(i); }
    void pay()           { requireStatus(Status.NEW); if (items.isEmpty()) throw ...; status = Status.PAID; }
    void ship()          { requireStatus(Status.PAID); status = Status.SHIPPED; }
    boolean isFinal()    { return status == Status.SHIPPED || status == Status.CANCELLED; }  // вычисляется
    // сеттеров нет: изменить состояние можно только через осмысленные операции
}
```

Для тенниса естественные объекты — матч, сет, гейм, тай-брейк. Каждый отвечает за свой уровень счёта.

**Вычислять, а не хранить.** Поле `isFinished` рядом с очками — второй источник правды: можно забыть его обновить,
и они разойдутся. Если «гейм завершён» можно вычислить из очков — вычисляй в методе (**Single Source of Truth**).

**Value Object для очков.** Очки в гейме — не `int` 0..4, где «3» надо помнить как «40», а тип с доменным смыслом:
`enum` со значениями LOVE, FIFTEEN, THIRTY, FORTY, ADVANTAGE (и, может, методом «следующее»). Компилятор не даст
записать туда «17».

**State для гейма и тай-брейка.** Гейм и тай-брейк считают очки **по-разному**. Один класс с `if (tieBreak)` в каждом
методе нарушает SRP. Это два класса с общим контрактом «начислить очко / завершён ли / кто выиграл». Сет решает,
какой из них создать следующим.

### 3. Три модели: домен, сущность, DTO

**Простыми словами.** В проекте будут три группы классов, похожих друг на друга. Их обязательно нужно разделять:

| | Доменная модель | JPA-сущность | DTO |
|---|---|---|---|
| **Зачем** | правила тенниса | хранение в БД | формат JSON API |
| **Знает про** | только теннис | таблицы, колонки | поля ответа из ТЗ |
| **Зависит от** | ничего (чистая Java) | JPA/Hibernate | Jackson (максимум) |
| **Пример** | матч с сетами и геймами, текущий счёт | `Match` с игроками и победителем | `{"firstPlayer": {...}, "winnerName": ...}` |

Почему не слить: таблица `Matches` по ТЗ хранит только игроков и победителя (без счёта!), а доменному матчу нужны сеты и геймы.
JSON по ТЗ хранит `"points": "AD"`, а домену удобен `enum`. Слитая модель тянет все три набора требований одновременно:
сломал одно — сломал всё. Игрок внутри домена — это **доменный** игрок (например, `record`), а не JPA-сущность.

Перекладывание между ними — **мапперы**. DTO содержат только примитивы, строки и другие DTO, никаких сущностей.

### 4. Потокобезопасность текущих матчей

**Простыми словами.** Текущие матчи лежат в мапе «UUID → матч» в памяти. Сервис — singleton-бин, запросы идут
параллельно из пула Tomcat. Две проблемы:
1. **Сама мапа.** `HashMap` при параллельной записи может сломаться. Нужна `ConcurrentHashMap`.
2. **Объект внутри мапы.** `ConcurrentHashMap` защищает только **свою структуру**, но не твой объект матча. Два запроса
   «очко игроку 1» одновременно выполнят `match.addPoint(...)` на одном объекте → гонка, счёт испорчен.
   Защищать надо операции над матчем: `synchronized` на объекте матча, атомарные методы CHM (`compute`/`computeIfPresent`
   выполняются атомарно для ключа), или блокировки.

```java
// Нейтральный пример: счета в памяти
Map<String, Account> accounts = new ConcurrentHashMap<>();
accounts.get(id).withdraw(100);               // ⚠️ мапа безопасна, но два withdraw на одном счёте — гонка
accounts.computeIfPresent(id, (k, acc) -> {   // ✅ функция выполняется атомарно для данного ключа
    acc.withdraw(100);
    return acc;
});
```

**Как проверить тестом:** `ExecutorService` на 10 потоков, `CountDownLatch`, чтобы все стартовали одновременно,
1000 начислений очков и проверка, что сумма очков сходится.

> 🎯 **Спросят на собесе:** Чем `ConcurrentHashMap` отличается от `Collections.synchronizedMap`?
> **Ответ:** `synchronizedMap` блокирует всю мапу на каждую операцию. CHM — неблокирующее чтение и блокировка на уровне
> бакета при записи (CAS + synchronized на узле в Java 8+), атомарные `compute*`/`merge`, слабо согласованные итераторы
> без `ConcurrentModificationException`. `null` ключи и значения в CHM запрещены.

### 5. TDD — разработка через тесты

**Простыми словами.** Цикл: **красный** (пишешь тест, который падает, потому что кода нет) → **зелёный**
(минимальный код, чтобы тест прошёл) → **рефакторинг** (улучшаешь код, тесты остаются зелёными). Для тенниса TDD
идеален: правила чётко формулируются тестами («при 40:40 очко даёт преимущество»).

Для удобства в тестах заведи **хелперы**: «довести гейм до 40:40», «выиграть N геймов подряд». Тогда тест тай-брейка
займёт 3 строки, а не 50 вызовов.

## Паттерны и принципы в фокусе

- **Rich Domain Model:** матч → сеты → гейм/тай-брейк; каждый знает свои правила и когда он завершён.
- **State / полиморфизм:** гейм и тай-брейк — разные классы.
- **Value Object + `enum`:** очки в гейме.
- **Single Source of Truth:** завершённость и победитель вычисляются.
- **Repository/DAO + разделение моделей.**
- **Трансляция исключений:** `HibernateException` не долетает до контроллера.

## Вехи

### Веха 4.1 — Доменная модель счёта (TDD, без фреймворков)

Самая важная веха проекта. Чистая Java: ни Spring, ни Hibernate, ни HTTP.

**Что нужно сделать**
1. Maven-проект `projects/04-tennis-scoreboard/`, пакет `domain`.
2. Классы, описывающие матч, сеты, гейм, тай-брейк, очки.
3. Операция «очко игроку N» на уровне матча и способы прочитать счёт.
4. 30+ тестов, сгруппированных `@Nested`: гейм, больше-меньше, сет, тай-брейк, матч.

**С чего начать.** С **самого нижнего уровня** — гейма без больше-меньше. Первый тест: «новый гейм — счёт 0:0».
Второй: «очко игроку 1 — 15:0». Дальше: «40:0 + очко → гейм выигран игроком 1». Потом больше-меньше. Только когда гейм
готов — сет, потом тай-брейк, потом матч.

**Вопросы для размышления**
1. Выпиши на бумаге все переходы счёта: 40:40 → AD → ровно/победа; 5:5 → 6:5 → 7:5; 6:6 → тай-брейк; тай-брейк 6:6 → разница 2.
   *Направление: каждый переход — будущий тест.*
2. Какие классы и какая ответственность у каждого? Кто знает про «разницу в 2»?
   *Направление: «разница в 2» есть и в сете, и в тай-брейке, и по сути в больше-меньше. Дублировать или вынести?*
3. Как внешний код узнаёт счёт, не имея возможности его изменить?
   *Направление: неизменяемый снимок (`record`) или только геттеры без сеттеров.*
4. Что происходит при попытке начислить очко в завершённом матче?

**Как проверить себя**
- [ ] 30+ тестов, все сценарии из ТЗ + твои граничные (особенно больше-меньше и тай-брейк 10:10 → 12:10).
- [ ] Нет сеттеров и публичных изменяемых коллекций; вместо `setPoints` — поведенческие методы.
- [ ] Гейм и тай-брейк — разные классы (или стратегии) с общим контрактом.
- [ ] Нет хранимого вычисляемого состояния (`isFinished`, `winner` как поля).
- [ ] Очки гейма — не голый `int`.

### Веха 4.4 — Очки и счёт

**Что нужно сделать.** `POST /matches/{uuid}/point`, `GET /matches/{uuid}`, ответ строго по формату ТЗ.

**С чего начать.** С маппера «доменный счёт → DTO из ТЗ» и юнит-теста на него (`"points": "AD"`, `tieBreakPoints` в тай-брейке).

**Вопросы для размышления**
1. Два запроса начисляют очко одному матчу одновременно. Что сломается и как защитить объект матча? *Направление: раздел 4.*

**Как проверить себя**

### Веха 4.5 — Сохранение завершённого матча

**Что нужно сделать.** Когда матч завершён — сохранить в БД и убрать из памяти.

**Вопросы для размышления**
1. В каком порядке: сначала сохранить, потом удалить из памяти, или наоборот? Что будет, если БД недоступна?
2. Где `@Transactional`? *Направление: мостик М4 — на публичном методе сервиса, без self-invocation.*

**Как проверить себя**
- [ ] Сохранение в одной транзакции; при ошибке БД матч не теряется.
- [ ] Ограничения БД (победитель — один из игроков, игроки разные) реально работают — проверь ручной вставкой некорректных данных.

### Веха 4.6 — Список завершённых матчей

**Что нужно сделать.** `GET /matches?page=&player_name=` по ТЗ.

**С чего начать.** Включи логирование SQL и сначала напиши запрос страницы без фильтра. Посчитай запросы.

**Вопросы для размышления**
1. Сколько SQL-запросов уходит на страницу из 10 матчей? Должно быть 2 (данные + count). *Направление: мостик М4, N+1 и `JOIN FETCH`.*
2. Где считается `offset` из номера страницы — в DAO или в сервисе? *Направление: чеклист ТЗ считает расчёт offset в DAO бизнес-логикой не на своём месте.*
3. Поиск по имени: точное совпадение или подстрока? Регистр? Какой индекс это поддержит?

**Как проверить себя**
- [ ] Пагинация на уровне SQL, стабильная сортировка, `totalPages`.
- [ ] Нет N+1 — приложи в описание вехи фрагмент лога SQL.
- [ ] Фронтенд из ТЗ работает со всеми 4 страницами.

- ★ **Параметры матча.** Best of 3 / best of 5, тай-брейк в решающем сете или нет — через конфигурацию, без `if` по всей модели.
- ★ **Счётчик SQL** через `datasource-proxy` или p6spy: в тестах DAO проверяй **количество** запросов (защита от N+1).
- ★★ **Оптимистическая блокировка.** Представь, что матчи хранятся в БД и инстансов приложения несколько. Как защититься от гонок?
  `@Version`, `OptimisticLockException`, retry.
- ★★ **Keyset-пагинация** вместо `OFFSET`. Когда `OFFSET` становится проблемой?
- ★★★ **Property-based тесты** (jqwik): случайные последовательности очков → инварианты (у победителя 2 сета, матч не продолжается после победы).
- ★★★ **Архитектурные тесты** (ArchUnit): контроллеры не импортируют entity, домен не зависит от Spring/Hibernate.

## За что будет 🔴

- Анемичная модель: вся логика подсчёта в сервисе.
- Один класс на гейм и тай-брейк с флагами. Очки как `int` 0..4.
- Сеттеры на доменных объектах; хранимое вычисляемое состояние.
- JPA-сущности в доменной модели, в DTO, в контроллерах. Lombok `@Data` на сущностях.
- `HashMap` для текущих матчей; гонка при начислении очков.
- N+1, пагинация в памяти, нет сортировки, `offset` считается в DAO.
- Сессия Hibernate на каждую операцию; `SessionFactory` создаётся больше одного раза или не закрывается.
- Креды БД в репозитории.
- Мало тестов подсчёта очков (особенно больше-меньше и тай-брейк).

## Контрольные вопросы (защита)

1. Rich vs anemic domain model. Покажи, где в твоём коде поведение, а где данные.
2. Почему домен, entity и DTO — три разные вещи? Что сломается, если их слить?
3. Как Hibernate понимает, что сущность изменилась? Что такое first-level cache?
4. N+1: как обнаружить и как лечить (3 способа)?
5. LAZY/EAGER, `LazyInitializationException`: когда возникает и как правильно лечить? Почему Open Session in View — не решение?
6. Как работает `@Transactional`? Propagation `REQUIRED` vs `REQUIRES_NEW`?
7. Скоупы бинов, жизненный цикл, почему singleton-бин должен быть stateless?
8. `ConcurrentHashMap` — что гарантирует и чего нет? Как ты защитил объект матча?
9. `DispatcherServlet`: путь запроса до контроллера (HandlerMapping, HandlerAdapter, MessageConverter).
10. Пагинация: `OFFSET` vs keyset.
